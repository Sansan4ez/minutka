# RFC: планка качества пилота (pilot quality bar)

## Status

**accepted (2026-07-30), поправки 2026-07-31 и 2026-08-06.** Фиксирует модель угроз и критерии качества для контура пилота (до 10–15 доверенных тестировщиков по приглашению оператора, single-owner) и правила обращения с review findings до конца пилота. Действует до триггера пересмотра (§7).

**Поправка 2026-08-06 (решение владельца).** В §2.2 добавлен п. 4 «Каждая задача называет misfit» — входной фильтр для задач, заведённых по инициативе агента, а не найденных ревью. Модель угроз §2.1, красные линии и бюджет ревью не менялись. Причина — §2.2 п. 4.

**Поправка 2026-07-31 (решение владельца).** Размер круга изменён с «3–5» на «до 10–15 приглашённых оператором»; триггер §7 (а) переформулирован с количественного на качественный. Модель угроз, красные линии §2.1 и бюджет ревью §2.2 не менялись. Причина — в §2.1.

## 1. Проблема

Ревью-процесс без зафиксированной планки качества по умолчанию применяет максимальную (enterprise/security-audit) строгость, и это остановило движение к пилоту. Факты на 2026-07-30:

- Фаза C.0 (`prs-jxy`): 49 подзадач, **шесть кругов ревью** по одной подсистеме. Фаза C.1: эпик `prs-mcn` + два ревью-эпика, `prs-2usv` — шестой раунд ремедиаций по одной ветке (R8–R27).
- 76 из 176 закрытых задач — баги, найденные ревью; пользовательских багов ноль, потому что пользователей ещё не было. ~159 из 341 коммитов — remediation/hardening/gate.
- Продуктовые эпики петли «рабочий день с ассистентом» (`prs-yjl`, `prs-jt0`, `prs-pdo`, `prs-t7c`, `prs-ip0`) созданы 2026-07-15/16 и не начаты.
- Соотношение в `src/` «функционал : защитная обвязка : инфраструктура» ≈ 1 : 1.6 : 4; из 13 md-процессов vault активны 2.

Типичные находки последних раундов — Unicode display controls в превью, provenance-поля в tool output, recovery-резерв до SDK-таймаута — относятся к враждебной модели угроз, которой у пилота нет. Definition of done дрейфовал от «сценарий работает» к «очередной аудит не нашёл замечаний»; каждая находка получала статус BLOCK, потому что критерия «достаточно для пилота» не существовало.

## 2. Решение

### 2.1. Модель угроз пилота

Контур: один инстанс runtime под управлением оператора; **до 10–15 доверенных тестировщиков, каждый — по персональному приглашению оператора**; каждый — single-owner своего контура; данные владельца **не враждебны** (владелец не атакует собственного ассистента).

**Почему 10–15, а не 3–5 (поправка 2026-07-31).** Качественно контур не изменился: участник по-прежнему приглашается лично оператором, самостоятельной регистрации нет, каждый остаётся single-owner своего контура, чужие данные ему недоступны. Изменилось только количество, а количество бьёт не по модели угроз, а по эргономике оператора: провижининг через `.env` и рестарт, который был приемлем для трёх человек, для пятнадцати превращается в основной источник ошибок. Поэтому вместо ужесточения модели угроз поправка требует убрать per-user конфигурацию из `.env` (расписания — из профиля и диалога, инвайты — через admin CLI). Красные линии не ослабляются; изоляция по `userId` (п. 1) при пятнадцати контурах становится не менее, а более значимой.

**Красные линии — обязательны всегда** (in scope, любая находка здесь блокирует):

1. Изоляция по `userId`: чужие данные не видны ни в одной проекции/инструменте.
2. Запись в stores — только через typed use-cases; агент не пишет напрямую.
3. Внешние/необратимые действия — только после явного подтверждения владельца.
4. Потеря или тихая коррупция durable-данных владельца.
5. Утечка секретов и токенов интеграций (в логи, в model context, в git).

**Вне скоупа до триггера пересмотра (§7)** — находки этих классов не блокируют фазы и уходят в post-pilot backlog:

- Unicode smuggling / display-control-атаки владельца на самого себя;
- prompt-injection через собственную историю диалога или собственный vault владельца;
- multi-instance гонки, HA, horizontal scaling;
- fail-closed-поведение на каждой внутренней границе (достаточно: ошибка видна и не нарушает красные линии);
- исчерпывающие allow-list'ы полей, видимых модели (кроме секретов из п. 5);
- изощрённый rate-limiting/DoS-защита сверх существующей.

### 2.2. Бюджет ревью

1. **Один раунд ревью на эпик + один integration gate.** Второй раунд — только по явному решению оператора, не по инициативе ревьюера/агента.
2. **Триаж каждой находки одним вопросом:** «нарушает ли это красную линию §2.1 или ломает пилотный сценарий для доверенного тестировщика?» Для границы между обратимой внутренней записью, деструктивной восстановимой операцией и внешним/необратимым действием используется таблица уровней подтверждения [RFC ассистента §9](./rfc-personal-assistant-architecture.md#9-внешние-действия-и-автономность). Да → задача в эпике. Нет → P3/P4 в post-pilot backlog без права блокировать фазу. Складируется отсеянное label'ом `post-pilot` + статусом `deferred` (см. §8): `prs-zgo` остаётся эпиком про удаление legacy, не свалкой находок.
3. Находки вне модели угроз §2.1 не получают статус BLOCK.
4. **Каждая задача называет misfit.** Триаж п. 2 работает на входе ревью — когда находка уже есть. На входе задачи действует то же правило: задача, пришедшая не от живого тестировщика (§2.3), заводится только с указанием конкретного расхождения с уже записанным assumption — ссылка на пункт RFC, брифа, процесса или на код. «Было бы правильнее», «обычно делают так», «понадобится потом» — не misfit; такая задача не заводится без решения оператора. Правило симметрично §3: как уже написанную обвязку не удаляют без причины, так и новую не добавляют без названного расхождения.
5. **DoD фазы:** продуктовый сценарий проходит end-to-end (spec или ручной прогон в Telegram) + `npm run verify` зелёный + красные линии соблюдены. Не входит в DoD: отсутствие замечаний повторного аудита.

### 2.3. Источник обратной связи после запуска

После запуска пилота приоритет отдаётся дефектам, о которые споткнулись живые тестировщики; они триажатся тем же вопросом §2.2 п. 2. Синтетические аудиты по инициативе агента не проводятся.

### Ограничения и принципы

- Планка **не** снижает границу безопасности внешних действий (RFC ассистента §9, бриф §11.3) — она остаётся красной линией.
- Планка касается только строгости ревью и приоритизации; качество реализации новых фич (типизация, specs на happy-path и ключевые ошибки) не меняется.

## 3. Что оставляем / что удаляем

| Что | Судьба |
|---|---|
| Уже написанная обвязка (timeout hierarchy, overflow recovery, confirmations, context budget, request integrity, экранирование) | **Оставляем как есть.** Написана, оттестирована, работает; удаление — отдельный непродуктовый риск |
| Наращивание обвязки сверх §2.1 | **Прекращаем** до триггера §7 |
| Открытые ревью-раунды (`prs-2usv`) | Закрываются по факту пройденного гейта; седьмой раунд не открывается |
| Упрощение/удаление legacy (`MinutkaService`, дубли стораджей) | Только в post-pilot cleanup (`prs-zgo`), не сейчас |

## 4. Влияние

- `AGENTS.md` — новый раздел «Планка качества пилота» со ссылкой сюда; правила §2.2 обязательны для всех агентов-ревьюеров.
- br: `prs-2usv` закрывается; success criteria `prs-yjl` (D.0) урезаются до single-instance slim; `prs-ip0` (P) урезается до usage/soft-limit; заводятся задачи реактивации процессов из legacy-registry.
- Существующие RFC не supersede: этот документ добавляет операционную планку, не меняя архитектурных решений.

## 5. Trade-offs

**Плюс:** выход на пилот за ~1.5–2 недели вместо бесконечной шлифовки; обратная связь от реальных пользователей вместо синтетических аудитов; проверка продуктовой гипотезы (бриф §15) начинает работать.

**Минус (принимаем осознанно):** известные теоретические дефекты вне §2.1 остаются открытыми в backlog; часть из них придётся закрывать перед выходом за доверенный круг. Альтернатива «сначала довести до аудиторской чистоты» отвергнута: она уже потребила две недели, не приблизив пилот, и не имеет естественного условия остановки.

## 6. Error handling & деградация

Решение документально-процессное; runtime-поведение не меняет. Backstop: если находка ошибочно ушла в backlog, а тестировщик о неё споткнулся, — она возвращается в работу по §2.3 обычным путём.

## 7. Не-цели и когда пересмотреть

- **Не** цель — ослаблять подтверждение внешних действий или изоляцию контуров.
- **Не** цель — запретить рефакторинг навсегда: `prs-zgo` исполняется после пилота.
- **Пересмотреть планку**, когда выполняется любое из: (а) выход за доверенный круг — self-service-подключение без участия оператора **либо** более 15 приглашённых; (б) первый платящий клиент вне круга; (в) подключение интеграции с правом внешних действий без человека в цикле; (г) импорт данных третьих лиц в контур владельца (внешний календарь: имена и темы встреч других людей). Триггер — полноценный security-аудит по текущей (враждебной) модели угроз и разбор накопленного post-pilot backlog.
- **Масштаб «50 пользователей» этой планкой не покрыт.** Он требует пересмотра по п. (а) заранее, а не постфактум: там появляются реальные вопросы изоляции между контурами, rate limiting, стоимости (иллюстративный расчёт по действовавшей на момент принятия ставке: soft-limit `$20`/владельца × 50 = потолок `$1000`/мес; актуальный default задан в `src/config/usage.ts` и `.env.example`) и поддержки. Планировать под 50 без пересмотра — значит принимать решение, которое эта планка не разрешает.
