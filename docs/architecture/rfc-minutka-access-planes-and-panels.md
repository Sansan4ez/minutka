# RFC: контуры доступа и панели «Минутки»

## Status

**proposed (2026-08-20).** Фиксирует ролевую модель внутреннего доступа (методолог, инженер продукта, администратор сервиса), состав будущих панелей и поэтапную организацию доступа к ним. Уточняет §2.1 [RFC исследовательского корпуса](./rfc-minutka-research-corpus-and-reporting.md), не заменяя его; сами панели остаются не-целью пилота и строятся только по триггерам §7.

- [RFC HTTP application API](./rfc-http-application-api.md) — модель принципала `operator{operatorId, permissions[]}` и директива отдельных `/v1/admin|operator/*` операций

## 1. Проблема

Ролевая модель в документации не совпадает с фактическим устройством работы, а эксплуатационная роль не описана вовсе:

- **Разделение «оператор участия / методолог» номинально.** §2.1 корпусного RFC перечисляет их как две роли, но сам же разрешает им быть одним доверенным человеком без отдельной RBAC-роли, а исторический дизайн панели относит заведение когорты и инвайты (`program-flow-and-cohort-setup`) к модулям методолога. Живой процесс один: методолог заводит поток, приглашает, сопровождает, анализирует и готовит отчёт. Документация же подталкивает проектировать «панель оператора» и «панель методолога» как разные продукты.
- **Роль администратора сервиса отсутствует в доках.** Кто контролирует доступность, логи, метрики, стоимость и лимиты — нигде не названо; неявно это «владелец инстанса» из планки качества. При этом эксплуатационный контур наполовину построен (systemd smoke/collector, `node_exporter` на loopback, usage-счётчик с soft limit, backup freshness) и обладает важным свойством — он content-free, — которое нигде не закреплено как граница.
- **Принадлежность traces не решена.** Trace viewer нужен для улучшения промптов и таксономии, но содержит рабочие разговоры (санитайзер секретов есть, PII-sanitizer — post-pilot). Отдать его «методологу вообще» — значит расширить содержательный доступ роли, которой для отчёта traces не нужны; отдать «администратору» — значит выдать содержание эксплуатационной роли.
- **Механика доступа не готова к второму человеку.** Один статический `MINUTKA_ADMIN_TOKEN`, `operatorId` захардкожен (`src/server/http/auth.ts:46`) — audit не может ответить «кто выгрузил корпус». Оператор не ограничен списком компаний: какой `companyId` передал, тот и получил. Research-контур доступен только локальными npm-скриптами с прямым доступом к Postgres.

Триггеры пересмотра не-целей уже записаны в корпусном RFC («web-панель — после первого полного цикла, если CLI/JSONL мешают»; «RBAC — при втором независимом исследователе»), но что именно строить по этим триггерам — не зафиксировано. Этот RFC закрывает развилку заранее, чтобы триггер запускал исполнение, а не проектирование.

## 2. Решение

### 2.1. Три плоскости доступа вместо пары «админ/методолог»

Внутренний доступ делится по **чувствительности данных**, а не по этапу работы с группой:

| Плоскость | Роль | Данные | Права (этап 2) |
|---|---|---|---|
| **Программная** | Методолог | Когорта end-to-end (справочники, инвайты, вовлечённость, ритм, lifecycle) + содержание corpus (messages, activities, evidence) + отчёт. Identity mapping участников живёт здесь. Всегда в пределах своих company/group. | `program:*`, `research:corpus`, `research:evaluation` |
| **Инженерная** | Разработчик продукта | Traces (payload, prompt/process/taxonomy versions), диагностика `trace_missing`, evaluation. Содержание видит, имена участников не нужны — работает на `subject_key`. | `research:traces`, `research:evaluation` |
| **Эксплуатационная** | Администратор сервиса | Health, логи (редактированные), метрики, стоимость и лимиты, бэкапы, миграции, retention. **Без содержания вообще.** | `ops:*` |

Инварианты:

- «Оператор участия» из §2.1 корпусного RFC — **функция методолога**, не отдельная роль. Отдельной «панели администратора» для программных операций не существует.
- **Эксплуатационная плоскость content-free by design** и обязана такой оставаться: метрики без owner id/content, access-логи только с `principal.kind`, usage — только метаданные токенов. Это позволяет делегировать эксплуатацию (например, devops-подрядчику), не выдавая corpus, traces и имена участников.
- Инженерная плоскость — часть **доверенной research-команды** («методологи и разработчики» из брифа), а не эксплуатация: traces — чувствительный контур, эксплуатационной роли не выдаётся.
- На пилоте все три плоскости — один доверенный человек; модель существует, чтобы при появлении второго человека выдать ему ровно одну плоскость без переписывания системы.

### 2.2. Traces: в контексте — методологу, browsing — инженеру

- В обзоре corpus методолог видит coverage и число `messagesMissingTrace` — как сигнал качества, без payload.
- Карточка evaluation case показывает связанный трейс **read-only**: case ссылается на `trace_id`, и метка `extractionCorrectness` без трейса не ставится.
- Свободный список/просмотр traces, разбор `trace_missing`, сравнение версий промптов — право `research:traces` инженерной плоскости.

Технически это одно право, а не отдельная панель: на пилоте — раздел меню того же человека; при разделении команды право просто не выдаётся методологу.

### 2.3. Панели

Одна web-панель с тремя разделами по плоскостям (строится по триггеру §7, скелет — исторический `methodologist-web-panel.md` с поправками ниже):

**«Группа» (методолог):** когорта (справочники, заведение потока), инвайты с одноразовой ссылкой и список участников с метками active/lagging/dropped_off (`listParticipants` + `participantEngagement`), запуск процессов по требованию и взведение финальных отчётов (`FinalReportArmingService.preview/arm`), corpus/evidence-навигация по `subject_key`/`roleId`/датам (`ResearchCorpusExportService`, `listResearchSubjects`), evaluation workbench с трейсом в карточке (`ResearchEvaluationService`), отчётная мастерская с confidence-метками и boundary preflight (`CompanyReportingService.exportGroup`), lifecycle-операции с двухшаговым подтверждением (`ResearchScopePurgeService`, `EmployeeDataDeletionService`).

**«Качество» (инженер):** trace viewer по scope (`ResearchTraceStore.list/get`), корреляция `trace_missing`, срезы evaluation-меток по версиям промптов, справочник активных prompt/process/taxonomy versions.

**«Эксплуатация» (администратор):** сводный health (smoke, юниты, миграции), audit-лента, агрегат usage по группе с cache-разбивкой и soft limit, artifact/MinIO-квоты. **Ядро эксплуатации web-панелью не дублируется:** systemd + journald + Prometheus через SSH-туннель — канонический путь; доращивается Grafana'ой и алертами, а не продуктом.

Поправки к историческому дизайну: заведение когорты — модуль методолога (подтверждается); правило «срезы <5 не показываются» заменено confidence-политикой (`signal ≥2 / confirmed ≥3·5·3`); модуль ручной рассылки напоминаний **не переносится** — рассылка superseded решением оператора 2026-08-19, автонапоминания шлёт только sweep.

### 2.4. Организация доступа: три этапа

**Этап 0 (сейчас, пилот).** CLI + SSH — канонический путь; панели нет. Эксплуатация — systemd + метрики через SSH-туннель. Ничего не меняется.

**Этап 1 (триггер: первый полный цикл показал, что CLI/JSONL мешают).**

- Одна панель поверх того же HTTP API; новые маршруты — отдельные неймспейсы `/v1/admin/*` и `/v1/research/*` по директиве [HTTP API RFC](./rfc-http-application-api.md): панель не переиспользует employee-эндпоинты с другим фильтром.
- Сеть: сервер остаётся на loopback; доступ — SSH-туннель или Tailscale/WireGuard. Публичной поверхности нет — та же модель, что принята для метрик.
- Аутентификация: map `operatorId → token` вместо единого `MINUTKA_ADMIN_TOKEN` (тот же паттерн, что `employeeTokens` в `auth.ts`). Каждое чтение/выгрузка содержания пишет audit-событие с персональным `operatorId` и scope, без payload.
- Разделы панели соответствуют плоскостям, но прав ещё нет: все токены равносильны (команда — по-прежнему доверенные люди уровня пилотной планки).

**Этап 2 (триггер: второй независимый человек в команде — методолог, разработчик или эксплуатационный подрядчик).**

- `operator{operatorId, permissions[]}` по уже спроектированной модели HTTP API RFC; плоскости из §2.1 становятся permission-группами.
- Scope-привязка методолога к списку его company/group: чтения вне списка отклоняются на авторизации, а не дисциплиной.
- Браузерная сессия: тонкий BFF с короткоживущей session-cookie + CSRF поверх тех же bearer-принципалов; при внешних людях — OIDC за TLS-реверс-прокси. Ротация и истечение токенов.

### Ограничения и принципы

- **Company delivery boundary.** Компания-клиент не получает доступа ни к одной плоскости; наружу уходит только проверенный report artifact. «Dashboard для компании» остаётся отвергнутым вариантом корпусного RFC.
- **Только typed use-cases.** Панель — ещё один транспорт над существующими сервисами; прямых SQL-чтений из UI-слоя нет. Tenant-изоляция (`assertExactScope`, композитные FK) остаётся единственным путём к данным.
- **Employee-only поля не всплывают:** `typicalTasks`/`aiLevel`/`programGoal`, приватный профиль, Telegram-данные — ни на одном экране. Личный `final_report` сотрудника — отдельный контур, его не видит ни методолог, ни компания.
- **Идентичность:** research- и инженерные экраны оперируют `subject_key`; identity mapping остаётся в программной плоскости. `subject_key` — не credential.
- **Audit факта, не содержимого:** принципал + scope + counts, без копии payload.
- **Необратимое — через preview → confirmation-строку** (паттерн `research-scope-purge` / `employee:data:delete` / `cycle:final-reports` переносится из stdin в модалку без изменения сервисов). Порядок конца цикла жёсткий: личные отчёты → артефакт компании → удаления.

## 3. Что оставляем / что удаляем

| Оставляем | Почему |
|---|---|
| CLI/npm-скрипты как канонический транспорт пилота | Работают, покрыты runbook'ами; панель — надстройка по триггеру, а не замена |
| Static bearer + loopback как Stage-1 baseline | Зафиксировано в HTTP API runbook; усиление привязано к этапам, а не к дате |
| Существующий стек наблюдаемости (systemd, `node_exporter`, SSH-туннель) | Content-free ядро эксплуатационной плоскости уже построено |
| Исторический `methodologist-web-panel.md` как скелет | Три поправки §2.3 вместо переписывания |

| Уходит | Почему |
|---|---|
| «Оператор участия» как отдельная роль | Функция методолога; отдельная роль порождала бы искусственную «панель администратора» для программных операций |
| Идея продуктовой web-панели для эксплуатации | Дублировала бы Grafana/Prometheus; в приложении остаются только health, audit-лента и usage-агрегат |
| Trace viewer как модуль методолога | Заменён трейсом в контексте evaluation case + правом `research:traces` инженерной плоскости |

## 4. Влияние

- [RFC исследовательского корпуса](./rfc-minutka-research-corpus-and-reporting.md) — §2.1 читается с уточнением этого RFC (роль оператора участия — функция методолога; добавлена эксплуатационная роль). Статус корпусного RFC не меняется.
- [RFC HTTP application API](./rfc-http-application-api.md) — §2.4 этого RFC становится планом реализации для уже описанной модели `operator{operatorId, permissions[]}`.
- [`methodologist-web-panel.md`](../diagram_modules/product-parts/methodologist-web-panel.md) — остаётся `historical`; при старте работ по этапу 1 скелет берётся оттуда с поправками §2.3.
- Код (по триггеру этапа 1): map операторских токенов в `auth.ts`; маршруты `/v1/research/*`; экспонирование готовых use-cases (subjects, traces, evaluation list, purge preview/commit); CRUD справочников + гранты `minutka_runtime` на `minutka_reference`; audit-события research-чтений с `operatorId`.
- План исполнения этапа 1 заводится **эпиком в `br`** со ссылкой на этот RFC; бэклог-порядок: именованные токены → `/v1/research/*` → evaluation workbench → lifecycle-маршруты → CRUD справочников → usage-агрегат и audit-лента → отзыв инвайта → персистентность отчёта → алертинг → статика/CORS + executable specs границ.

## 5. Trade-offs

- **Одна панель с разделами vs отдельные приложения по ролям.** Одна панель дешевле и честнее для команды из 1–3 человек; риск — соблазн «показать всё всем» — снимается тем, что разделы с этапа 1 ходят в разные неймспейсы, и permission-разрез этапа 2 ложится на готовые границы. Отдельные приложения отвергнуты как преждевременная сложность.
- **Инженеру — содержание traces.** Альтернатива (маскировать payload для инженера) отвергнута: улучшение извлечения без содержания невозможно, а инженер — часть той же доверенной research-команды с consent-покрытием. Цена — ещё один человек с содержательным доступом; смягчение — отдельное право, audit фактов и PII-sanitizer в post-pilot roadmap.
- **Эксплуатация без web-панели.** Плюс: не строим и не сопровождаем дубль Grafana. Минус: администратору нужны две поверхности (панель для usage/audit, туннель для метрик). Принято: обе поверхности живут за одним SSH/VPN-контуром.
- **Loopback + туннель vs публичный вход с логином.** Туннель не создаёт публичной поверхности и не требует session-механики на этапе 1; цена — панель недоступна «с телефона без настройки». Публичный вход отложен до этапа 2 и только за TLS-прокси.

## 6. Error handling & деградация

- Панель — необязательный транспорт: при её недоступности CLI-путь остаётся полным (ни одна операция не существует только в панели). Это инвариант этапа 1: новые операции сначала появляются как use-case + CLI/HTTP, потом как экран.
- Отказ audit-записи при research-чтении через панель обрабатывается как сейчас в export-контуре: операция не выполняется молча без следа.
- Компрометация одного операторского токена с этапа 1 лечится отзывом одной записи map, а не заменой общего секрета.
- Просроченный/отозванный токен получает 401 с редактированным телом — как существующие ошибки HTTP-контура.

## 7. Не-цели и когда пересмотреть

- **Не строить панель сейчас.** Триггер — из корпусного RFC: первый полный цикл «пилот → отчёт» показал, что CLI/JSONL мешают работе. До того панель не заводится даже задачей.
- **Не строить RBAC сейчас.** Триггер — второй независимый человек любой плоскости (методолог, разработчик, эксплуатационный подрядчик).
- **Не кабинет компании.** Пересматривается только вместе с моделью delivery boundary корпусного RFC, не этим документом.
- **Не эксплуатационная web-панель** (Grafana-дубль). Пересмотреть, если эксплуатацию примет человек без SSH-доступа — тогда сначала пересматривается сама модель доверия, потом инструмент.
- **Не ручная рассылка напоминаний из панели.** Superseded-решение оператора 2026-08-19 действует; пересматривается только живым вмешательством оператора.

## 8. Открытые вопросы

1. Механика браузерной сессии этапа 2: BFF с session-cookie или OIDC за прокси — решается при триггере по составу команды (внутренние люди → BFF, внешние → OIDC).
2. Хранение и версионирование подготовленного client report — общий вопрос с §10.2 корпусного RFC; панель этапа 1 может работать с отчётом «на лету», но фиксация решения о передаче требует персистентности.
3. Нужен ли второму методологу вариант программной плоскости **без** identity mapping (только `subject_key` + статусы) — возникает, если сопровождение группы и анализ corpus разделятся между людьми раньше, чем ожидается.
4. Стек алертинга поверх существующих метрик (Prometheus alertmanager vs простой systemd-таймер с уведомлением) — эксплуатационное решение, RFC не блокирует.
