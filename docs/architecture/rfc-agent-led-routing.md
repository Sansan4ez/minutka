# RFC: агент-ведомый роутинг (lightweight)

> **Унаследованный фундамент клона.** Документ описывает runtime персонального ассистента, на котором построена «Минутка». Живые продуктовые решения, мультитенантная ось и privacy-границы «Минутки» задаёт [RFC мультитенантного контура](./rfc-minutka-tenancy-and-reporting.md).


## Status

**Accepted для пилота-прототипа (2026-07-15); implemented baseline в A.2 (2026-07-16).** Сильный personal-assistant agent сам роутит по процессам в один ход; отдельный пре-флайт-LLM-роутер не участвует в product chat-path. Process/tool audit восстанавливается из фактического typed-tool исполнения. Это уточнение (и частичный откат) к `rfc-personal-assistant-architecture.md` §8; legacy-роутер остаётся только во внутреннем контуре совместимости «Минутки» и не является конкурирующим runtime-путём ассистента.

Установка проекта: это **рабочий прототип, не enterprise**. Тестируем лёгкую, простую, понятную и быструю архитектуру — и именно поэтому ожидаем от неё надёжности и эффективности. Сложность добавляем только когда её потребует наблюдаемая боль, а не заранее.

Related:
- [RFC ассистента](./rfc-personal-assistant-architecture.md) (§8 реестр навыков, §9 автономность)
- [Research: уроки ecom1-process-architect](../../researches/rfc-ecom1-process-architect-lessons-for-time-agent.md) (§3.2.1 роутинг, §7 уроки)

## 1. Проблема

Прообраз (`ecom1-process-architect`) устроен так: умный агент **сам** внутри одной сессии читает `index.md`, выбирает 1–3 бизнес-процесса, читает их и выполняет задачу через один контролируемый tool-boundary. Детерминированный код там отвечает только за **инфраструктуру** (какую версию инструкции подгрузить, изоляция, аудит) — но **не** за семантический выбор «какой процесс нужен этому запросу».

Наш код уехал в другую модель:

- отдельный LLM-вызов `conversationDecisionAgent` возвращает strict JSON (`selectedProcessIds` + `workDecision` + `insightDecision`) — то есть **решает за агента**, что тому делать;
- вокруг вырос TS-слой марашлинга: `resolveAgentManualSelection`, `sanitizeConversationDecision`, `ensureLifecycleProcesses`, хардкод-каталоги id в 3 местах;
- основной агент запускается с `toolChoice: "none"` и по сути **рендерит текст** по уже принятым за него решениям.

Итог: **два LLM-вызова и толстая прослойка** там, где прообраз обходится одним ходом. Детерминизм сел в неправильный слой — в задачный семантический роутинг, который сильный агент делает сам. Симптом — сам план F1–F8 (F2 «registry не source of truth, список продублирован», F3 «два конкурирующих роутера», F6 «порядок не фиксирован», F8 «нет проверки синхронизации»): это не восемь багов, а техдолг разросшейся машинерии.

Усугубляющий фактор: почти вся тяжёлая часть роутера (`workDecision.mode==="boundary"`, захардкоженные строки отказов в `buildBoundaryResponse`, guardrails, company-leak, min-group-size) обслуживает **отказную модель Минутки**. Ассистент по `rfc-personal-assistant-architecture.md` §1.1 эти ограничения **снял** (писать черновики — можно; внешние действия — с подтверждением; single-owner). Мы чистим (F1–F8) и расширяем (F2 как предусловие Phase B) мозг, который новый продукт по большей части должен удалить.

## 2. Решение

**Агент сам роутит и действует в один ход.** Детерминированный код обеспечивает только границу и изоляцию, а не выбор процессов.

1. **Один ход агента.** В prompt — `core` (маленький) + `processes/index.md` (маленький). Агент сам решает, какие процессы применимы, и читает их: инлайн (процессы по 60–150 строк) или через `readProcess(id)`-tool. Отдельный пре-флайт-LLM-роутер как основной механизм — не используется.
2. **Действие — через typed tools, чей хендлер и есть use-case.** Граница записи, аудит и изоляция по `userId` живут в хендлере инструмента, а не в пре-флайт-роутере. Инструмент сам по себе — контролируемая граница (аналог единственного `execute_python` в ecom1).
3. **Audit / `selectedProcessIds` — восстанавливаются из фактических вызовов инструментов** (а после появления `readProcess` — также из его лога), а не задаются Application-слоем заранее и не создаются отдельным решающим артефактом. Это подход самого ecom1 («runtime BP восстанавливаются из последовательности Read/tool logs») и research §3.2.1.
4. **Детерминированные `if` — только для реально детерминированных гейтов:** «нет профиля → онбординг», «пришёл файл → capture-путь». Это дешёвые ветки, не LLM-роутер.

### `toolChoice` — скоупится, а не глобальный `"none"`

`toolChoice: "none"` в чат-пути ставился ради безопасности внешних действий. Но внутренняя обратимая запись владельца — это строка «автоматически в личном контуре» из таблицы автономности (RFC §9), её безопасно разрешить. Поэтому:

- **разрешённые инструменты** — внутренние обратимые записи в личном контуре владельца (`captureIdea`, заметки, черновики);
- **под подтверждением остаются** внешние/необратимые действия (отправка адресату, календарь, финансы) — они не выдаются агенту как свободный tool-loop, а инициируются явным confirm-шагом (RFC §9 без изменений).

Красная линия: агент **никогда** не пишет в store в обход typed use-case и никогда не выполняет внешнее действие без подтверждения. Меняется механизм роутинга, не граница безопасности.

## 3. Что оставляем (заработано)

| Инвариант | Как обеспечивается |
|---|---|
| Агент не пишет в stores напрямую | Запись только в хендлере typed-инструмента = use-case |
| Изоляция по `userId` | Ownership-constraint в store; проекции только для аутентифицированного владельца |
| Тестируемость без LLM | Инжектируемый `AgentRunner` + in-memory stores; spec мокает runner и проверяет вызов инструмента + состояние store |
| Allow-list навыков | Обеспечивается на уровне tool-хендлера (инструмент принимает только известные project/type/id), а не отдельным пре-флайт-роутером |

---

## 4. Что удаляем / не наращиваем

- **Пре-флайт `conversationDecisionAgent` как основной механизм** и его JSON-контракт решений — пока навыков единицы.
- **TS-слой марашлинга**: `resolveAgentManualSelection`, `sanitizeConversationDecision`, `ensureLifecycleProcesses`, дублирующиеся хардкод-каталоги id.
- **Захардкоженную продуктовую логику в TS**: строки отказов `buildBoundaryResponse`, lifecycle-форсинг — уезжает в process-файлы/агента.
- **Второй конкурирующий роутер** (`agent-manual-router*`) — удаляется вместе с первым, а не сводится к одному (F3 растворяется).

Порядок удаления — миграционный (§6), не «большой взрыв».

## 5. Влияние на Phase B

План B (br-эпик `prs-2yr`, задачи B1–B5) — слим-вариант:

- **Оставляем:** доменный `Classified`, порт `IdeaStore` + in-memory + PostgreSQL-адаптер, миграцию `0011`, изоляцию по `userId`, `SPEC-PERSONAL-ASSISTANT-INBOX-001`.
- **Схлопываем** отдельный `InboxClassifierRunner` (третий агент) + `IngestionService.captureInbox` + детерминированный форс `inbox_capture` → **агент + один инструмент** `captureIdea(project, type, summary, nextStep, needsClarification)`, хендлер = use-case `IngestionService` (запись в `IdeaStore`, изоляция, аудит, сборка ответа). Агент сам читает owner context, включая `03_мои_проекты.md` / `06_классификатор.md`, решает, известен ли проект, и при отсутствии уверенности передаёт `БЕЗ_ПРОЕКТА`. Application-слой не разбирает семантику этих Markdown-файлов.
- **Убираем предусловие F2 целиком:** без пре-флайт-роутера не нужно чинить хардкод-каталог, чтобы протолкнуть id `inbox_capture`.

Тестируемость сохранена: spec инжектирует mock-runner, который на вход X зовёт `captureIdea` с аргументами Y; проверяет состояние `IdeaStore`, изоляцию, ответ и фолбэк. «Правильно ли LLM сроутил» specs и сейчас не проверяют (роутер в specs замокан) — потери покрытия нет.

## 6. Влияние на F1–F8 и порядок работ

Заход F1–F8 (ex `fix-routing-catalog`, теперь br-эпик `prs-x5q`) пересматривается: большая часть пунктов **растворяется**, а не выполняется.

| Пункт | Судьба при агент-ведомом роутинге |
|---|---|
| F2 (единый каталог id + `assertPurpose`) | Не нужен как предусловие B: нет пре-флайт-роутера, который его требует |
| F3 (два роутера) | Оба роутера удаляются, а не сводятся к одному |
| F6 (порядок selectedProcessIds) | Порядок задаёт сам агент/индекс; отдельная точка сортировки не нужна |
| F1 (`/docs` как runtime-вход) | Остаётся как гигиена документации (дёшево) |
| F4 (формулировка privacy) | Остаётся: точное privacy-правило в `AGENTS.md`/`privacy-boundary.md` |
| F5 (extractor process-driven) | Пересматривается на Фазе G в новой модели |
| F7/F8 (drift-проверки каталога) | Резко упрощаются: меньше дублей — меньше что синхронизировать |

Порядок: **не делать заход F1–F8 как предусловие Phase B.** Сначала слим-Phase B на новой модели → по факту увидеть, какие из F1–F8 вообще остались осмысленными.

## 7. Не-цели и когда пересмотреть

- **Не** вводим пре-флайт-LLM-роутер обратно, пока навыков единицы.
- **Возвращаем** его точечно, только когда одновременно: (а) навыков много и (б) наблюдается мисс-роутинг одного агента на specs/проде — ровно триггер из `rfc-personal-assistant-architecture.md` §11 («add LLM classifier only if specs show need»).
- **Не** трогаем границу безопасности §9: скоупинг `toolChoice` касается только внутренних обратимых записей владельца.
