# RFC: архитектура персонального AI-ассистента

## Status

**Proposed (черновик для пилота).** Документ фиксирует целевую архитектуру нового продукта — персонального AI-ассистента руководителя — построенного на архитектуре текущего `time-agent` («Минутка»). Продукт переиспользует runtime, application-слой, хранилища и Agent Vault «Минутки», расширяет их до широкого ассистента и добавляет один новый слой: личный vault пользователя с многоканальным приёмом файлов.

«Минутка» в её текущем узком виде (вечерний дневник) может остаться отдельным продуктом. Новый проект **не тащит** её ограничения роли и её company/methodologist privacy-модель: он с самого начала проектируется как полноценный ассистент с одной ролью.

## 1. Контекст и задача

Бриф описывает персонального ассистента для предпринимателя: единая точка входа для задач, идей и контекста; система навыков (планирование, банк идей, дайджесты, встречи, «совет директоров», контент, финансы); Telegram как основной канал; постепенное накопление контекста; human-in-the-loop для внешних действий.

Архитектура «Минутки» уже даёт бо́льшую часть фундамента:

- Mastra-runtime и каналы Telegram / HTTP / CLI поверх общего application-слоя;
- application-owned state в PostgreSQL (профиль, история, consent, feedback, insights, audit);
- constrained decision router с allow-list процессов — по сути готовый оркестратор навыков;
- Agent Vault: статические git-файлы (`AGENTS.md`, `processes/`, `docs/`) + проекции изменяемого состояния в `/proc`, `/run`;
- `AgentRunner` + executable specs, позволяющие тестировать весь путь без LLM;
- контроль побочных эффектов: `toolChoice: "none"` в основном chat-path, мутации через use-cases.

Новый продукт требует четырёх добавлений:

1. **Личный vault пользователя** — изменяемая файловая папка, наполняемая из TG, генерации по опросу и внешней загрузки по `userId`.
2. **Расширенный каталог навыков** с генерацией материалов и внешними действиями (календарь, задачи, дайджесты, контент).
3. **Планировщик фоновых задач** — утренний дайджест, вечерний и недельный обзоры.
4. **Классификатор контекста** (две оси: проект × тип) как сквозная модель для задач, идей, материалов и расходов.

### 1.1. Чем ассистент отличается от «Минутки»

| Свойство | «Минутка» | Ассистент |
|---|---|---|
| Роль | Вечерний дневник рабочего дня | Полноценный «второй пилот» |
| Писать за пользователя | Запрещено | Разрешено (черновики: посты, КП, follow-up) |
| Вечерняя рефлексия | Основной сценарий | Один из процессов |
| Извлечение/агрегация контекста | Company/methodologist reporting, агрегаты групп ≥5 | **Индивидуальная фича**: показать пользователю его рутину и кандидатов на автоматизацию |
| Privacy-модель | Трёхсторонняя (сотрудник/методолог/компания) | Single-owner: один владелец видит всё своё |
| Внешние действия | Нет | Есть, через подтверждение |
| Хранилище контента | Только typed stores + проекции | Гибрид: MinIO (документы/блобы) + PostgreSQL (записи) |

## 2. Цели и не-цели

### Цели

1. Переиспользовать application-слой, router, stores, Agent Vault и runtime «Минутки» без форка ключевых механизмов.
2. Дать пользователю личную папку, доступную агенту, с надёжной изоляцией по `userId` и тремя каналами наполнения.
3. Сохранить принцип «application владеет состоянием»: агент не пишет напрямую и не выполняет внешние действия без подтверждения.
4. Сделать каждый навык добавляемым как process-файл + запись в реестре, без изменения ядра.
5. Держать всё тестируемым без LLM (in-memory адаптеры для новых stores, mock `AgentRunner`).

### Не-цели (для пилота)

- Полная юридическая privacy-контура, экспорт/удаление по регламенту — отдельный контур позже.
- Веб-дашборд и мобильное приложение (этап 2–3 брифа).
- Автономные внешние действия без подтверждения.
- Произвольный shell/выполнение кода агентом (Daytona/Sandbox — позже).
- Каталог из десятков навыков до проверки базового сценария.

## 3. Целевая архитектура

```text
Telegram / HTTP / внешний загрузчик (по userId)
                    │
                    ▼
        IngestionService  (единая точка записи)
          ├─ документы-контекст → DocumentStore   (MinIO {userId}/context/)
          ├─ блобы (чеки, транскрибации, файлы) → BlobStore (MinIO {userId}/inbox/)
          └─ структурные записи (идеи/задачи/расходы) → PostgreSQL record stores
                    │
                    ▼
        AssistantService  (application orchestration)
                    │
                    ▼
        ConversationDecisionRouter → выбор навыков (registry allow-list)
                    │
                    ▼
        Runtime projections:
          /proc/profile   /proc/context   /proc/records
          /proc/inbox     /proc/decision  /run/actions
                    │
                    ▼
        AssistantAgent (Mastra) → ответ или черновик
                    │
                    ▼
        Внешние действия и мутации → typed use-cases + подтверждение + audit
```

Компоненты, переиспользуемые из «Минутки» как есть: `ConversationStore`, `ProfileStore`, `ConsentAcceptanceStore`, `FeedbackStore`, `InsightStore`, `AuditEventStore`, `ConversationDecisionRouter`, `MinutkaContextBuilder` (обобщается до `AssistantContextBuilder`), `AgentRunner`, HTTP/SDK/CLI транспорт.

Новые компоненты: `DocumentStore`, `BlobStore`, record stores (`IdeaStore`, `TaskStore`, `ExpenseStore`), `IngestionService`, `SchedulerService`, MinIO-адаптеры, набор навыков в vault.

## 4. Роль агента и профиль пользователя

### 4.1. Роль агента

Одна роль — ассистент. Определяется в `vault/AGENTS.md` (новый неймспейс продукта). В отличие от «Минутки», роль **разрешает** генерацию материалов и внешние действия, но сохраняет границы:

- всё, что уходит вовне (сообщение адресату, публикация, изменение календаря, финансовая операция), — только после явного подтверждения пользователя;
- материалы, сгенерированные агентом, по умолчанию имеют статус «черновик»;
- фактические данные (имена, цены, сроки) не выдумываются — берутся из личного vault или уточняются;
- духовный/личный слой конституции пользователя не выносится во внешние тексты (правило из `01_личная_конституция.md`).

### 4.2. Профиль пользователя

Профиль — это набор документов-контекста в личном vault (см. §5), а не одна анкета. Минимальный набор (из §5 брифа):

- **личная конституция** — роли, ценности, стиль общения, ограничения;
- **цели и приоритеты** на период;
- **проекты** и **продукты/услуги**;
- **характер ассистента** (persona, tone of voice);
- **классификатор** (проекты × типы);
- **источники** для дайджеста.

Профиль заполняется маленькими шагами через онбординг (переиспользуем `onboarding-profile-extractor`) и уточняется в диалоге. Persona влияет только на тон и длину ответа, не на границы.

## 5. Личный vault пользователя

Гибридная модель хранения: разный контент — разное физическое хранилище, но единый логический неймспейс, проецируемый в контекст агента.

### 5.1. Три уровня контента

| Уровень | Что | Хранилище | Доступ агента |
|---|---|---|---|
| Документы-контекст | Конституция, цели, проекты, характер, классификатор, источники | MinIO `{userId}/context/*.md` | Свободное чтение (bounded-проекция в prompt); правка через онбординг/подтверждение |
| Рабочие записи | Идеи, задачи, встречи, расходы | PostgreSQL (typed stores) | Чтение через проекции; запись через use-cases |
| Блобы и артефакты | Фото чеков, `.vtt`/`.txt` транскрибации, загрузки, сгенерированный HTML-дайджест | MinIO `{userId}/inbox/*`, `{userId}/artifacts/*` | Чтение по ссылке; запись через ingestion/генерацию |

Почему именно так:

- **документы** — их мало, они markdown, читаются целиком → объектное хранилище идеально, версионирование через MinIO object versioning;
- **записи** — их много, они структурированы, по ним нужны запросы («идеи без движения 7 дней», «сколько действий типа `ДЕНЬГИ` за неделю») → нужен SQL;
- **блобы** — бинарные и крупные → объектное хранилище с изоляцией префиксом.

### 5.2. Логический неймспейс

Расширяем vault-неймспейс «Минутки» под ассистента:

```text
/AGENTS.md        роль ассистента и глобальные границы            (git)
/processes/*      навыки продукта                                  (git)
/docs/*           активные runtime-документы                       (git)
/proc/profile     профиль текущего пользователя                    (проекция)
/proc/context     bounded-срез документов-контекста                (проекция над DocumentStore)
/proc/records     bounded-срез рабочих записей                     (проекция над record stores)
/proc/inbox       недавние необработанные входящие                 (проекция над BlobStore)
/proc/decision    решение router                                   (проекция)
/bin/*            typed actions (мутации, внешние действия)         (git-манифесты + TS)
/run/actions      audit/action trace                               (проекция)
```

`/processes`, `/docs`, `/AGENTS.md`, `/bin`-манифесты — общие для всех пользователей git-файлы (это продукт). Всё персональное живёт в MinIO/PostgreSQL и попадает в prompt только bounded-проекцией. Сырые персональные данные в git не коммитятся (правило из `agent-vault.md`).

### 5.3. Изоляция

- MinIO: единый bucket, ключи с префиксом `{userId}/`; доступ через application-слой, агенту не выдаются креды bucket'а.
- PostgreSQL: ownership-constraint по `userId` во всех record stores (как `employeeId` в «Минутке»).
- Проекции строит `RuntimeProjectionBuilder` только для аутентифицированного `userId`; агент не может подставить чужой id (модель из RFC runtime-projections).

## 6. Контракты stores

Новые stores следуют паттерну репозитория: `interface` + `in-memory` адаптер (для specs) + продакшн-адаптер (MinIO/PostgreSQL).

### 6.1. Классификатор (сквозной тип)

```ts
// Ось 1: проект (из 03_мои_проекты.md / классификатора). Расширяемый список.
type ProjectCode = string; // "АССИСТЕНТ" | "БНВ" | "КОРП" | ... | "БЕЗ_ПРОЕКТА"

// Ось 2: тип действия по сути (06_классификатор.md)
type RecordType =
  | "money"        // 💰 ДЕНЬГИ (привилегированный тип)
  | "development"  // 🔨 РАЗРАБОТКА
  | "content"      // 📣 КОНТЕНТ
  | "people"       // 🤝 ЛЮДИ
  | "operations"   // ⚙️ ОПЕРАЦИИ
  | "knowledge"    // 🧠 ЗНАНИЯ
  | "personal";    // ❤️ ЛИЧНОЕ

interface Classified {
  project: ProjectCode;   // обязателен; "БЕЗ_ПРОЕКТА" ⇒ агент обязан спросить
  type: RecordType;       // обязателен
}
```

### 6.2. DocumentStore (MinIO — документы-контекст)

```ts
interface UserDocument {
  userId: string;
  path: string;          // "context/01_личная_конституция.md"
  content: string;       // markdown
  version: string;       // MinIO version id
  updatedAt: string;
}

interface DocumentStore {
  get(userId: string, path: string): Promise<UserDocument | null>;
  put(userId: string, path: string, content: string): Promise<UserDocument>;
  list(userId: string, prefix?: string): Promise<UserDocument[]>;
  delete(userId: string, path: string): Promise<void>;
}
```

### 6.3. BlobStore (MinIO — блобы и артефакты)

```ts
interface StoredBlob {
  userId: string;
  key: string;           // "inbox/2026-07-15/receipt-8a1f.jpg"
  contentType: string;
  size: number;
  createdAt: string;
}

interface BlobStore {
  put(userId: string, key: string, body: Buffer, contentType: string): Promise<StoredBlob>;
  get(userId: string, key: string): Promise<{ blob: StoredBlob; body: Buffer } | null>;
  presignGet(userId: string, key: string, ttlSeconds: number): Promise<string>;
  list(userId: string, prefix?: string): Promise<StoredBlob[]>;
}
```

### 6.4. Record stores (PostgreSQL — рабочие записи)

```ts
interface Idea extends Classified {
  id: string;
  userId: string;
  summary: string;         // суть одной строкой
  source?: string;         // ссылка/файл-ключ в BlobStore
  status: "raw" | "discussed" | "planned" | "done" | "dropped";
  createdAt: string;
  lastActivityAt: string;  // для запроса «без движения N дней»
}

interface Task extends Classified {
  id: string;
  userId: string;
  title: string;
  dueDate?: string;
  status: "open" | "in_progress" | "done" | "cancelled";
  originIdeaId?: string;   // связь «идея → задача → продажа»
  createdAt: string;
}

interface Expense {
  id: string;
  userId: string;
  amount: number;
  currency: string;
  merchant?: string;
  category: string;        // предложенная категория
  date: string;
  receiptKey?: string;     // ключ в BlobStore
  createdAt: string;
}

interface IdeaStore {
  add(idea: Omit<Idea, "id" | "createdAt" | "lastActivityAt">): Promise<Idea>;
  list(userId: string, filter?: Partial<Classified> & { status?: Idea["status"] }): Promise<Idea[]>;
  stale(userId: string, days: number): Promise<Idea[]>;      // «созрело / без движения»
  update(userId: string, id: string, patch: Partial<Idea>): Promise<Idea>;
}
// TaskStore, ExpenseStore — аналогично.
```

Все мутации record stores вызываются только из application use-cases, не агентом напрямую.

## 7. Ingestion: три канала, одна точка записи

Все три пути наполнения личного vault идут через `IngestionService` — единственную точку записи. Агенту не даётся произвольная запись (принцип «Минутки»).

```text
Канал                         → что делает IngestionService
Telegram (голос/фото/ссылка/  → STT при необходимости → классификация входящего
  пересланное/текст)             (идея/задача/материал/чек) → запись в нужный store
Генерация по опросу           → онбординг-экстрактор → DocumentStore (context/*)
  (онбординг)
Внешняя загрузка по userId    → валидация владельца → BlobStore (inbox/*)
  (web/API)                      → постановка задачи на обработку
```

Классификация входящего из Telegram — это навык `inbox_capture` (§8), реализующий `бизнес-процесс_входящий_поток.md`: определить тип, предложить категорию (проект × тип), сохранить, подтвердить коротко, предложить следующий шаг. Внешние действия из этого потока (покупки, брони) — только предлагаются.

## 8. Реестр навыков

> **Уточнение (2026-07-15): роутинг — агент-ведомый.** См. [rfc-agent-led-routing.md](./rfc-agent-led-routing.md) — основной документ для механизма выбора навыков. Реестр и триггеры ниже сохраняются как каталог, но выбор процессов делает **сам агент в один ход** (core + index + typed tools), а не отдельный пре-флайт-LLM-роутер. Описание strict-JSON-роутера в §8.2 — отложенный механизм, возвращается только при много-навыковом мисс-роутинге (§11).

Навык = process-файл в `vault/processes/` + запись в `registry.json` с полем `appliesTo` (триггер). Механизм уже существует в «Минутке»; расширяем список триггеров.

### 8.1. Стартовый набор (MVP пилота, §10 брифа)

| Навык (process id) | Источник в vault | `appliesTo` | Результат |
|---|---|---|---|
| `onboarding` | (из «Минутки») | `onboarding_first_response` | Профиль, цели, стиль |
| `inbox_capture` | `02_банк_идей/входящий_поток` | `chat` | Идея/задача/материал сохранены и классифицированы |
| `day_focus` | §6.2 брифа | `chat`, `scheduled` | План дня, приоритеты, перепланирование |
| `morning_digest` | `01_дайджест/утренний_дайджест` | `scheduled`, команда | HTML/текст дайджест в Telegram |
| `meeting_followup` | `03_встречи/после_встречи` | `file_uploaded`, пересланный файл | Конспект, action items, черновик follow-up |
| `board_of_directors` | `04_совет_директоров/council/SKILL.md` | команда «собери совет» | Многопозиционный разбор, 3 первых шага |
| `evening_reflection` | (из «Минутки») | `chat`, `scheduled` | Итоги дня, перенос незавершённого |
| `context_insights` | insight extraction «Минутки» | после ответа | Индивидуальная карта рутины/автоматизации |

### 8.2. Новые триггеры router

Сейчас router знает `chat`, `onboarding_first_response`, `feedback`. Добавляем:

- `scheduled` — запуск из `SchedulerService` (дайджест, обзоры);
- `file_uploaded` — приход файла (`.vtt`/`.txt`/фото) через ingestion.

Триггеры `scheduled`/`file_uploaded` — это детерминированные гейты входа (какой путь запустить), а не LLM-роутер: файл → capture-путь, расписание → запуск навыка планировщиком. Выбор *содержательных* процессов внутри хода делает сам агент. Allow-list (агент не может придумать несуществующий навык) обеспечивается на уровне tool-хендлера — инструмент принимает только известные id/типы (см. [rfc-agent-led-routing.md](./rfc-agent-led-routing.md) §2–3). Прежний strict-JSON-роутер (`selectedProcessIds` + решение о допустимости + insight-флаг) — **отложенный** механизм: возвращается точечно, только когда навыков много И наблюдается мисс-роутинг одного агента (§11).

### 8.3. Формат навыка

Тот же контракт, что в `process-authoring.md` (`When applies / Inputs / Process / Outputs / Privacy notes / Anti-patterns / Dependencies`). `council/SKILL.md` уже написан в совместимом skill-формате и переносится почти как есть, его `frameworks.md` — как dependency-документ.

## 9. Внешние действия и автономность

Реализуем таблицу автономности из §11.3 брифа через `/bin`-манифесты + typed use-cases + audit:

| Действие | Режим |
|---|---|
| Сохранить заметку/идею/черновик/дайджест | Автоматически в личном контуре |
| Создать/изменить задачу или событие календаря | Предложить → подтверждение |
| Отправить сообщение внешнему адресату | Только после подтверждения текста и получателя |
| Подключить интеграцию, выдать доступ | Только пользователь |
| Финансовое/публичное/юридически значимое | Только пользователь; агент готовит черновик |

Каждое внешнее действие проходит через use-case, фиксируется в `AuditEventStore` и проецируется в `/run/actions`. В основном chat-path сохраняется `toolChoice: "none"`; действия инициируются через явные подтверждающие шаги, а не свободный tool-loop.

Внешние интеграции пилота: Google Calendar, Telegram, файловое хранилище, загруженные транскрибации (§11.2). Часть доступна как MCP-инструменты, но вызываются они через application use-cases, а не отдаются агенту напрямую.

## 10. Планировщик фоновых задач

`SchedulerService` — фоновый воркер (в проекте пока нет; `digests.ts` — это HMAC-утилита, не планировщик). Запускает навыки с триггером `scheduled`:

- утренний дайджест 09:00–09:30 мск (per-user timezone);
- вечерняя рефлексия;
- недельный обзор банка идей и целей (пятница).

Каждый запуск идёт тем же путём, что и сообщение пользователя: `AssistantService → router → навык → результат в Telegram`. Для пилота (<100 пользователей) достаточно одного воркера с расписанием в PostgreSQL; вынос в очередь — позже.

## 11. Приватность (single-owner)

Модель проще, чем у «Минутки»: один владелец видит все свои данные, кросс-пользовательской агрегации нет.

- изоляция по `userId` на уровне MinIO-префикса и PostgreSQL-constraint;
- проекции строятся только для аутентифицированного владельца;
- секреты интеграций (токены календаря и т.п.) — вне vault, в защищённом хранилище;
- «данные никуда не утекают» в коммуникации — только после технического и юридического подтверждения (§12 брифа);
- индивидуальная карта рутины/автоматизации (`context_insights`) считается по данным самого пользователя и показывается ему же — это фича, а не company reporting.

Полный юридический контур (retention, экспорт, удаление по регламенту) — вне пилота, отдельным этапом.

## 12. Тестируемость

Сохраняем модель «Минутки»: `AgentRunner` инжектируется, executable specs гоняют весь путь `CLI → SDK → Server → AssistantService → mock AgentRunner` без LLM. Новые stores получают in-memory адаптеры (`InMemoryDocumentStore`, `InMemoryBlobStore`, `InMemoryIdeaStore`, ...), поэтому ingestion, классификация, проекции, router и навыки покрываются specs без сети и без MinIO. Реальные MinIO/провайдер-вызовы проверяются отдельными smoke-тестами.

## 13. Фазовый план

| Фаза | Содержание | Проверяемый результат |
|---|---|---|
| A. Каркас | MinIO-адаптеры (`DocumentStore`, `BlobStore`), `IngestionService`, `AssistantService` поверх application-слоя, vault-неймспейс ассистента, `/proc/context` проекция | Пилотный пользователь (Максим): онбординг пишет конституцию в vault, агент читает контекст |
| B. Банк идей | Навык `inbox_capture`, `IdeaStore`, классификатор, запись из Telegram (текст/голос/ссылка/фото) | «Ничего не терять»: любое входящее классифицировано и сохранено |
| C. Планирование | Навык `day_focus`, `TaskStore`, подключение Google Calendar через use-case | «Что мне делать сейчас» за 2–5 минут |
| D. Дайджест | `SchedulerService`, навык `morning_digest`, источники из vault, HTML-артефакт в `BlobStore` | Автоматический дайджест 09:00 в Telegram |
| E. Встречи | Навык `meeting_followup`, приём `.vtt` через ingestion, `artifacts/` | Конспект + action items + черновик follow-up |
| F. Совет директоров | Перенос `council` как навыка | Разбор развилки с 3 первыми шагами |
| G. Индивидуальные инсайты | Навык `context_insights` над записями и историей | Карта рутины и кандидатов на автоматизацию для пользователя |

Фазы A–F покрывают «набор для пилота» из §10 брифа и демо «один день с ассистентом» (§9). Каталог не расширяется дальше до подтверждения удержания на базовом сценарии.

> **При составлении плана реализации каждой следующей фазы держаться агент-ведомой модели [rfc-agent-led-routing.md](./rfc-agent-led-routing.md).** Заход «Гигиена роутинга/каталога» (ex fix-routing-catalog, F1–F8; теперь br-эпик `personal-assistant-x5q`) **superseded**: большинство дефектов — техдолг пре-флайт-роутера и растворяется вместе с ним (F2 больше не предшественник Фазы B; F3/F6 отпадают). Остаются как дешёвая гигиена F1 и F4; F5/F7/F8 пересматриваются в новой модели. План новой фазы указывает только реально оставшиеся предусловия, а не весь F1–F8.

## 14. Принятые решения (пилот)

Зафиксировано 2026-07-15.

1. **Репозиторий — один, монолит.** Продукт живёт в одном репозитории и одном деплое. Код уже расслоён (`domain / application / infrastructure / mastra / server / telegram`), что даёт модульность без стоимости нескольких сервисов. Выделение общих пакетов — только если позже понадобится гонять «Минутку» и ассистента как два продукта из общей библиотеки.

2. **Векторный поиск — отложить.** Документов-контекста мало и они выбираются явной проекцией по путям. Если поиск понадобится раньше — включить полнотекстовый поиск Postgres (`tsvector`), он не требует расширения. `pgvector` добавляется отдельной миграцией `0011_*`, когда вырастет корпус «материалов» и keyword-поиск начнёт промахиваться.

3. **Timezone и расписание.** `timezone` (IANA, напр. `Europe/Moscow`) — поле `UserProfile`, собирается в онбординге (дефолт из локали Telegram, иначе спросить). `SchedulerService` для пилота — один фоновый воркер; расписание в PG (`userId, kind, time_of_day, timezone, next_run_at`), `next_run_at` считается в TZ пользователя. Перед реализацией оценить встроенный примитив **Mastra Schedules** как альтернативу ручному воркеру.

4. **Секреты интеграций — `.env` + один `INTEGRATION_ENC_KEY`.** Инфраструктурные секреты — через `.env` (как сейчас в `env.ts`). Per-user OAuth-токены (календарь и т.п.) хранятся **зашифрованными at-rest** в таблице `integration_credentials(userId, provider, ciphertext, …)` через AES-GCM (`node:crypto`, тот же примитив, что HMAC в `digests.ts`), ключ — `INTEGRATION_ENC_KEY` из `.env`. Токены **никогда** не попадают в vault, логи и prompt; агент инициирует действие через use-case, а тот расшифровывает и вызывает API на сервере. Ротация ключа — отдельная задача. Внешний secret-store (Infisical: self-host, dynamic secrets, KMS) — рассмотренный апгрейд на будущее, для пилота избыточен.

5. **Модель и лимиты.** Единая модель для всех агентов — **`openai/gpt-5.5`** с `providerOptions.openai.reasoningEffort: "high"` (задаётся в `llm.ts` и на агентах). Тиринг дешёвой моделью отложен до появления usage-данных. Учёт: per-user таблица `usage` в application-слое (токены/стоимость на запрос, сумма за месяц) с мягкой деградацией при превышении (предупредить → притормозить дорогие навыки → отказать). Для дашбордов/алертов по стоимости используется встроенная observability Mastra (метрики токенов/латентности; требует OLAP-store — DuckDB локально, ClickHouse в проде). Жёсткий предохранитель (`CostGuardProcessor` / `TokenLimiter`) — позже, как технический слой.

### Инструменты разработки

**Mastra Studio** (`npm run dev` → `localhost:4111`) используется как средство разработки, отладки и наблюдаемости: playground агентов (живое переключение моделей, reasoning-трейсы, scorers), визуализация workflow, инспекция процессоров (guardrails/token-limiters), MCP-серверы, метрики стоимости. Это **не** runtime: продакшн-путь Telegram идёт через `AssistantService` с privacy-проекциями, поэтому end-to-end приватность проверяется executable specs, а Studio — итерацией над навыками и промптами.
