# RFC: ежедневный ритм «Минутки»

## Status

**accepted (2026-08-19), до запуска следующей внешней группы.** RFC фиксирует два плановых касания — утреннее планирование и вечернюю рефлексию — и добровольную дневную корректировку без отдельного расписания. Реализация выполняется в задаче `mnt-cycle-completion-4gd.8`.

## 1. Проблема

Продуктовый baseline задаёт ежедневный цикл из утреннего планирования, добровольной дневной корректировки и вечерней фиксации фактической работы. Сотрудник должен получать непосредственную пользу от планирования и рефлексии, а исследовательский контур — регулярные structured activities для доказательной карты автоматизации.

Текущий runtime этому циклу не соответствует:

- `morning_activity_collection` утром ретроспективно спрашивает об активностях с прошлого касания вместо планирования нового дня;
- `evening_reflection` намеренно read-only и не создаёт structured activities;
- отключённый `day_focus` умеет выделять до трёх приоритетов и один следующий шаг, но зависит от унаследованного task/project-контура, который не входит в первую версию «Минутки»;
- два default schedule уже существуют, но фактические данные собираются утром, а не в естественной точке вечернего подведения итогов;
- отдельное третье push-касание увеличивает нагрузку на группу из семи сотрудников, хотя дневная переприоритизация нужна только при реальном изменении ситуации.

Из-за этого утро не выполняет обещание сотруднику, вечер не является стабильным producer данных, а добавление дневного расписания без наблюдаемых данных создаёт риск fatigue.

## 2. Решение

### 2.1. Два плановых касания

Default rhythm содержит ровно два scheduled process по рабочим дням в timezone сотрудника:

1. `morning_planning` — утреннее планирование;
2. `evening_reflection` — вечерний факт и рефлексия.

Текущее пользовательское время, timezone, набор дней и enabled state сохраняются при переводе расписания `morning_activity_collection` на `morning_planning`. Базовые времена остаются около текущих значений: утро — `08:30`, вечер — `19:00`. Сотрудник может перенести или отключить каждое касание существующим owner-scoped typed use-case.

Третьего default schedule нет.

### 2.2. Утро: `morning_planning`

Утренний процесс:

- помогает сформулировать не более трёх приоритетов или намерений на день;
- предлагает ровно один конкретный первый шаг;
- не выдумывает встречи, сроки, доступность, проекты и обязательства;
- не использует task/project tools;
- не вызывает `collectActivity` для planned или не начатой работы;
- сохраняет continuity через canonical conversation и bounded thread history, а не через отдельный task store.

`day_focus` не реактивируется. Из него переносятся только продуктово полезные правила:

- не более трёх приоритетов;
- один наблюдаемый следующий шаг;
- явное обозначение нехватки контекста;
- запрет выдумывать сроки, встречи и обязательства.

В `morning_planning` не переносятся list/mutation task tools, project ranking и логика владельца персонального ассистента.

### 2.3. День: добровольный `midday_adjustment`

`midday_adjustment` является chat-only процессом и запускается только по инициативе сотрудника. Он не входит в scheduled process ids и не имеет default push.

Когда сотрудник сообщает об изменении ситуации, процесс:

- использует bounded thread history, включая утренний план, если он доступен;
- сравнивает новый ввод с утренними намерениями;
- помогает выбрать практичную переприоритизацию без оценки продуктивности;
- остаётся read-only и не создаёт task/project records;
- не записывает планы и намерения как фактические activities.

Если утреннего плана в bounded history нет, процесс отвечает по текущему сообщению и не выдумывает исходный план.

### 2.4. Вечер: основной producer фактических activities

`evening_reflection` является основным стабильным producer structured activities ежедневного цикла. Плановое сообщение приглашает назвать:

- что фактически выполнялось;
- какой получен результат;
- что мешало или повторялось;
- явный work-related energy/stress signal, если сотрудник считает его значимым.

После ответа процесс:

- вызывает `collectActivity` ровно один раз на каждую названную фактическую активность, не более трёх за один turn;
- не записывает planned, неначатую или выдуманную работу;
- оставляет неизвестные поля пустыми;
- сохраняет препятствие и energy/stress marker только из явного сообщения сотрудника и в рамках действующего закрытого контракта activity;
- отражает результат без оценки продуктивности и предлагает не более одного небольшого следующего шага.

Conversation остаётся каноническим источником полного содержания, activity — канонической структурированной записью фактической работы, trace — evidence пути обработки. Отдельного extractor или dual-write не появляется.

### 2.5. Пропущенный вечер

Если вечернего ответа нет, следующее утреннее касание может задать один короткий необязательный catch-up-вопрос о вчерашней фактической работе до планирования нового дня.

Catch-up применяется только когда bounded context не показывает уже записанную вечернюю activity за соответствующий день. Ответ может создать activities через `collectActivity` по тем же правилам, что вечерний процесс. Без ответа система ничего не выдумывает и переходит к утреннему плану.

Catch-up является деградацией пропущенного вечернего ответа, а не третьим scheduled touch.

### 2.6. Метрики первой недели

Оператор оценивает первую рабочую неделю по participant-days. Eligible participant-day — день сотрудника с завершённым онбордингом и включённым соответствующим расписанием.

Обязательные метрики:

- delivery rate отдельно для утра и вечера: успешно доставленные касания / eligible scheduled fires;
- response rate отдельно для утра и вечера: ответы на касание / успешно доставленные касания;
- activities per responding employee для вечернего касания;
- количество добровольных midday updates и distinct сотрудников, которые их отправили;
- количество distinct сотрудников, отключивших касание;
- количество явных жалоб на частоту или навязчивость.

Delivery failure считается операционной проблемой и не интерпретируется как отказ сотрудника от ритма.

### 2.7. Триггеры пересмотра

После первой рабочей недели оператор пересматривает формулировку, время или частоту, если выполнен хотя бы один критерий:

- вечерний response rate ниже `50%` успешно доставленных вечерних касаний;
- не менее двух distinct сотрудников из группы отключили касания или явно назвали два касания навязчивыми.

Delivery rate ниже `95%` запускает разбор доставки и scheduler/runtime, но сам по себе не меняет продуктовый ритм.

Малое число добровольных midday updates само по себе не является основанием добавлять push. Третье scheduled touch рассматривается отдельным решением только когда вечернего coverage недостаточно, fatigue не наблюдается и сотрудники явно подтверждают полезность дневного напоминания.

### Ограничения и принципы

- Планы не становятся фактическими activities.
- Фактическая activity создаётся только по названной сотрудником работе.
- Structured writes идут только через typed use-case `collectActivity`.
- `day_focus` и task/project tools остаются вне model-visible контура «Минутки».
- Ни один процесс не оценивает продуктивность и не сравнивает сотрудников.
- Компания получает только подготовленный report artifact; изменение ритма не меняет research/client boundary.
- Текст разговора, activities и traces остаются находимыми для purge, recompute и evaluation.

## 3. Что оставляем / что удаляем

| Существующее решение | Судьба |
|---|---|
| Два default schedule | Оставляем: утро и вечер |
| `morning_activity_collection` как active morning process | Заменяем на `morning_planning` с миграцией пользовательских настроек |
| `evening_reflection` | Оставляем и добавляем typed collection фактических activities |
| `day_focus` | Оставляем отключённым; переносим только четыре узких правила планирования |
| Bounded thread history | Оставляем как continuity утро → день → вечер |
| `collectActivity` | Оставляем единственным structured writer ежедневного цикла |
| Отдельный midday push | Не добавляем |
| `midday_adjustment` | Добавляем как chat-only read-only процесс |
| Отдельный task/project store для плана | Не добавляем |
| Утренний catch-up после пропущенного вечера | Добавляем как необязательную деградацию без расписания |

## 4. Влияние

Задача `mnt-cycle-completion-4gd.8` реализует решение и синхронизирует:

- scheduled/diagnostic process ids и default schedules;
- миграцию существующих утренних schedule rows;
- `vault/assistant/processes/registry.json`, process manuals и index;
- active tool ownership для `collectActivity`;
- scheduled prompts и onboarding welcome;
- Telegram labels и schedule management;
- executable/persistence specs утро → день → вечер → missed evening;
- [карту возможностей](../product/skills-map.md);
- runbooks scheduled process и пилотного прогона.

До реализации текущая карта возможностей продолжает описывать фактический `morning_activity_collection`; RFC описывает принятое целевое решение и не выдаёт его за уже работающую capability.

Пункт 5 открытых вопросов superseded [RFC мультитенантного контура](./rfc-minutka-tenancy-and-reporting.md) закрывается этим решением: вечерний процесс нужен и становится основным producer фактических structured activities.

## 5. Trade-offs

**Получаем:**

- прямое соответствие обещанию сотруднику: план утром, факт вечером;
- устойчивый ежедневный источник evidence для карты автоматизации;
- меньший риск fatigue без обязательного дневного push;
- повторное использование существующего scheduler и bounded thread history;
- отсутствие возврата task/project-контура персонального ассистента.

**Принимаем:**

- при пропуске вечера фактических данных может не быть до следующего утра;
- добровольный midday update даёт нерегулярную статистику и не является гарантированным producer;
- утренний план хранится как conversation context, а не как отдельная queryable domain entity;
- качество связывания дневного апдейта с планом ограничено bounded history.

Отвергнут вариант трёх ежедневных push: он повышает нагрузку на семь участников без подтверждённой нехватки данных. Отвергнут вариант оставить сбор утром: он смешивает ретроспективный факт и новый план и откладывает данные на следующий день. Отвергнут возврат `day_focus`: он возвращает task/project capabilities, которые не входят в продуктовую границу первой версии.

## 6. Error handling & деградация

- Scheduled delivery failure фиксируется в `schedule_fires`; система не считает его отсутствием ответа и не меняет ритм автоматически.
- При недоступной утренней истории `midday_adjustment` не выдумывает план и работает только с текущим сообщением.
- При пропущенном вечере утро предлагает один catch-up-вопрос; отсутствие ответа не блокирует планирование.
- Ошибка `collectActivity` не должна терять conversation turn; structured collection остаётся видимо неуспешной и может быть размечена исследователем вручную.
- Неизвестная длительность, система, категория или препятствие остаётся пустым значением.
- Миграция расписания сохраняет пользовательские настройки; конфликт или невозможность однозначной миграции не создаёт третью schedule row и требует явного operator-visible результата.

## 7. Не-цели и когда пересмотреть

Не входят в это решение:

- третье плановое касание;
- выходные касания по умолчанию;
- отдельная domain entity дневного плана;
- task/project/calendar integrations;
- wellness-процесс, шкала настроения и восстановительные практики;
- автоматическая оценка качества или продуктивности сотрудника;
- автоматическая смена расписания по метрикам без решения оператора.

Ритм пересматривается после первой рабочей недели только по метрикам §2.7 либо по зафиксированной обратной связи живых участников. Расширение не обосновывается формулировкой «может понадобиться позже».

## 8. Открытые вопросы

1. Нужен ли после первого цикла отдельный queryable personal-day state, если bounded history окажется недостаточно для недельных сводок.
2. Какой текст вечернего приглашения даёт лучший response rate без ощущения контроля.
3. Нужно ли после первой недели изменить default time, не меняя число касаний.
