# Контракт сборки runtime context персонального ассистента

> **Статус:** implemented baseline C.0 (2026-07-28). Канонизирует фактический runtime и целевую сборку по [RFC персонального ассистента](./rfc-personal-assistant-architecture.md) и [agent-led routing](./rfc-agent-led-routing.md). Эпик `prs-jxy` закрыт; новые источники и capabilities добавляются следующими фазами без пересмотра базовых trust/budget инвариантов.

## Назначение

Runtime context собирает только явно зарегистрированные источники. Порядок задаёт приоритет доверия, но не превращает пользовательские данные в инструкции. Capability set передаётся отдельно как typed tools и не сериализуется в prompt.

README-файлы каталогов не являются prompt-источниками. `vault/assistant/docs/README.md`, `bin/README.md`, `proc/README.md` и `run/README.md` — только developer documentation: список trusted policy задаёт `vault/assistant/processes/registry.json`, а фактический список возможностей — request-scoped typed tools. В owner context специальное навигационное имя — только точное `INDEX.md`; оно остаётся untrusted data, а не policy.

## Канонический порядок

1. **Base Mastra instructions.** Минимальная скрытая роль bridge-агента; продуктовая политика здесь не дублируется.
2. **Trusted product control plane.** `/AGENTS.md`, allow-listed `/docs/*`, `/processes/index.md`, затем зарегистрированные process-файлы. Пока весь малый каталог помещается в ceiling, он загружается целиком как стабильный trusted-префикс. Ленивые ссылки/read-инструмент вводятся только если каталог перестанет помещаться; до этого отдельный механизм не нужен.
3. **Owner-scoped projections.** В целевом порядке: `/proc/profile`, приоритетный `/proc/context`, relevant `/proc/records`, `/proc/inbox`, `thread_summary`, recent conversation history. Все эти источники — данные текущего authenticated owner, а не authority. В частности, owner workflows под `/proc/context/99_system/workflows` читаются только по необходимости как reference data.
4. **Diagnostic data.** `/run/actions` отсутствует в обычном запросе и добавляется только для явного diagnostic/recovery сценария; он никогда не используется как policy source.
5. **Request-scoped typed tools.** Capability set передаётся runtime-мостом отдельно от текста; наличие process-файла не выдаёт capability.

## Registry источников и бюджеты

Общий budget для текстового `systemContext`: **88 000 Unicode characters** по умолчанию, с резервом ответа **8 000** и статическим допуском **2 000** на headings/fences/separators renderer-а. Канонические defaults определены в `src/application/context-budget.ts`; deployment `.env.example` не задаёт их активными значениями, а показывает только закомментированные примеры overrides. Каждый source ceiling измеряет уже фактически rendered секцию источника. Для `/proc/context`, `/proc/records` и recent history это headings, safety notices, XML wrappers/attributes, escaped owner content и optional truncation/degradation marker; projection builders и финальная сборка prompt используют одни exact renderers. `applyContextBudget` как defense-in-depth отклоняет любую непустую секцию выше собственного ceiling независимо от trust class, а не включает невалидный prompt. Конфигурация принимается только если сумма ceilings гарантированных источников (`base_instructions`, `agent_manual`, `/proc/profile`, `/proc/context`, machine index) + максимальный user input + response reserve + wrapper allowance помещается в total; `applyContextBudget` fail-fast отклоняет over-ceiling/non-fit любого гарантированного источника и никогда не добавляет его в omitted list. Поэтому `/proc/context` и machine index присутствуют в каждом owner chat при валидных bounded projections. Ceilings источников, лимиты проекций, глубина machine index и document-tool limits конфигурируются через `ASSISTANT_CONTEXT_*` / `ASSISTANT_DOCUMENT_*`; невалидная или противоречивая конфигурация отклоняется при старте до открытия внешних ресурсов. В частности, ceilings `context` и `context_index` обязаны вмещать minimum viable generated sections для пустого owner tree: production renderer `/proc/context` всё равно выдаёт trusted heading и safety notice, а machine-index renderer — heading, trust notice, read hint, view metadata и `(empty)` tree. Минимумы вычисляются запуском этих же renderer functions, а не отдельными magic constants; точная граница принимается, ceiling ниже неё завершает startup с именем source, вычисленным minimum и configured ceiling без owner data.

## Реактивное восстановление при overflow провайдера

Статический budget остаётся основной гарантией, но provider context-window error запускает ровно **один** повтор того же agent turn. Повтор детерминированно пересобирает `systemContext` через `createContextBudgetConfig`: exact rendered ceilings `records`, recent `history` и `/proc/context` machine index уменьшаются до 3 000 chars, число records — до 8, recent turns — до 4, глубина index — до 2. `base_instructions`, assistant manual, `/proc/profile`, основной `/proc/context` и `thread_summary` не уменьшаются; LLM-компакшн не выполняется.

Классификатор принимает OpenAI/Anthropic-подобные сообщения о context length, слишком длинном prompt/input и превышении token limit, включая вложенные `cause/error/response` Mastra errors. `429`, rate-limit, quota и throttling явно не считаются overflow и не ретраятся. Перед единственным retry пишется metadata-only `overflow_recovery` с причиной, номером попытки и применёнными ceilings, без prompt/user text. Retry разрешён только пока request-scoped mutation effect state равен `none`. Непосредственно перед вызовом `captureIdea` state становится `attempted`, а `committed` — только после успешного ответа. В состоянии `attempted` неизвестно, состоялась ли durable запись: application не повторяет agent turn и fallback capture, а возвращает typed `mutation_outcome_unknown` с просьбой сначала проверить список идей. В состоянии `committed` application также не повторяет agent turn и fallback capture, а выбрасывает typed `context_overflow` с честным сообщением, что идея сохранена. Если повторный overflow произошёл в состоянии `none`, fallback `captureIdea` сохраняет исходный ввод ровно один раз, а transport явно сообщает владельцу об ограничении контекста вместо тихой деградации. Кумулятивные output-character и physical-byte document-tool budgets между попытками не сбрасываются.

## Матрица типов запросов

| Тип запроса | Фактический runtime | Целевой runtime |
|---|---|---|
| `chat` / Telegram text | base prompt + assistant manual (`/AGENTS.md`, allow-listed `/docs`, process index/files) + `/proc/profile` + приоритетный `/proc/context` + `/proc/records` + optional `thread_summary` + bounded recent history; request-scoped typed tools | добавить relevant `/proc/inbox`; `/run/actions` только по необходимости |
| `onboarding` | legacy identity/onboarding service собирает legacy manual/profile context и генерирует first response; product `AssistantService` в этот ход не вызывается | personal-assistant control plane + onboarding profile/draft data; после подтверждения материализовать profile/core context через typed use-case |
| `voice intake` | STT выполняется transport-слоем, затем транскрипт идёт в тот же `chat` path с `inputModality=voice` | тот же chat contract + релевантная inbox/artifact metadata без raw provider payload |
| `file intake` | бинарный файл сохраняется детерминированно в `ArtifactStore`; agent turn сейчас не выполняется | сохранение остаётся transport/use-case gate; optional typed post-processing получает control plane + `/proc/inbox` item и узкий toolset |
| `scheduled job` | product runtime отсутствует | control plane + `/proc/profile` + `/proc/context` + relevant `/proc/records`/`inbox`; synthetic request payload; только job-specific tools |
| `callback` | consent/onboarding/feedback обрабатываются deterministic typed use-cases без product-agent prompt | сохранять deterministic путь; agent context не собирать, если callback не требует отдельной генерации текста |

## Инварианты loader и renderer

- Registry schema строгая и версионированная; неизвестные поля отклоняются.
- Core и index имеют фиксированные allow-listed paths. Runtime docs и process files — только прямые дети соответствующих каталогов.
- Loader fail-fast отклоняет дубли `id` и дубли `path`, отсутствующие файлы и registry entries, которых нет в index.
- Index не является источником файлов: загрузка идёт только по registry.
- Repository `docs/**`, `vault/user/**`, storage keys `context/*`/`inbox/*` и raw database/object-storage paths не загружаются в system context.
- Owner projections экранируются и маркируются как untrusted data. Их scope формирует application layer из authenticated `userId`/`threadId`; имя `INDEX.md`, legacy `AGENTS.MD`/`README.MD` или каталог `99_system` не повышают trust. Owner workflows из `99_system/workflows` — on-demand reference data: auto-slice не получает специального механизма исключения. Если workflow должен управлять поведением ассистента, его переносят в trusted process-файл и регистрируют в `vault/assistant/processes/registry.json`.
- Приоритеты документов `/proc/context` загружаются только из versioned trusted-манифеста [`vault/assistant/proc/context-priorities.json`](../../vault/assistant/proc/context-priorities.json); owner context не участвует в выборе или изменении правил.
- Machine index `/proc/context` строится только из `DocumentStore.listMetadata`, стабильно сортируется по логическому `/proc/context/*` path и не читает тела объектов. Projection также не вызывает full-body `DocumentStore.list`: request-local budget точечных `get()` равен `contextDocuments`, включает core reads и поэтому ограничивает body reads как O(config) независимо от размера vault. До `get()` projection считает exact rendered metadata reference и безопасную metadata-only нижнюю границу full fragment (UTF-8 size допускает не меньше `ceil(bytes / 4)` Unicode scalars); если ни full, ни reference не могут поместиться, body не читается. После исчерпания read budget оставшиеся документы обрабатываются только по metadata: reference при fit, иначе aggregated size-only audit; полная карта остаётся в machine index. Каждый owner-controlled path segment рендерится как JSON-quoted data с дополнительным escaping `<`, `>`, `&` и backtick, поэтому имя не может создать Markdown heading/fence или XML-like tag; обычный logical path остаётся однозначно восстанавливаемым для `readDocument`. Если file tree не помещается, renderer целиком переключается на folder rollup, затем на top-level rollup и, наконец, на fixed-size global rollup с total documents/bytes, root-file count и top-level-folder count без имён. Folder/top-level views агрегируют root-level files, когда rollup короче перечисления. Тихая обрезка запрещена; выбранная ступень фиксируется metadata-only audit reason вплоть до `global_rollup`.
- Для навигации агент начинает с machine index, затем при входе в папку читает её точный `INDEX.md`, если он есть, и только после этого целевые документы. `INDEX.md` — короткая owner/agent-authored аннотация смысла и точки старта только для прямых детей папки; он не перечисляет структуру вглубь и не дублирует размеры/существование файлов из machine index. Import drift-check применяет одно правило к Markdown-ссылкам и path-like code spans, оканчивающимся на `.md`, `.txt`, `.vtt` или `/`: путь должен существовать, быть relative, exact-case и прямым ребёнком текущей папки.
- Core-документы, совпавшие с trusted priority manifest, валидируются при discover/import/migration пилотной БЗ против единого UTF-8 byte maximum, count и rendered ceilings: byte rule всегда считает фактически декодированный content через `Buffer.byteLength(content, "utf8")`, а общий renderer считает XML-escaped content, path/representation wrappers, safety notice и section markup тем же кодом, который затем строит prompt. Все planned writes проходят полный preflight до первой записи. Core остаётся полным только при fit; невалидные данные отклоняются до записи в store, а runtime для existing oversized core сохраняет понятный throw до agent call как defense-in-depth без тихой обрезки или `index-reference`. Existing oversized non-core legacy object остаётся metadata-visible и без body read деградирует в `index-reference`; для допустимых non-core runtime тем же rendered-cost выбирает full → truncation → index-reference, сохраняя детерминированную лестницу и metadata-only audit без текста owner documents.
- Калибровка capacity планирования: для русскоязычного текста используется консервативная оценка около **2 Unicode chars/token**; character ceilings остаются исполнимой границей, token ratio — только sizing guidance. Стабильные секции prompt не содержат request id, timestamp или других volatile-полей: это сохраняет общий префикс пригодным для provider prompt caching; volatile scope остаётся в runtime data после trusted control plane.
- При `readDocument.truncated=true` агент продолжает с `nextOffset` до `truncated=false`; крупные документы читает прицельно через section/search. `searchDocuments` стабильно сортирует logical metadata и сначала проверяет case-insensitive literal path: такой результат имеет `matchedBy="path"`, `snippet=null`, не читает body и не расходует output/scan budgets; документ, совпавший также по content, возвращается один раз как path match. Только metadata entries без path match проходят output/maximum-size/scan gates и content read, а content result имеет `matchedBy="content"` и bounded snippet. Exhausted/oversized gates не останавливают последующий metadata path matching, но глобальные `readBudgetExhausted`, `scanBudgetExhausted`, `documentTooLarge` и `truncated` честно отмечают неполный content search. Для read/search `readBudgetExhausted=true`, `scanBudgetExhausted=true` или `documentTooLarge=true` означают, что полноту content чтения/поиска нельзя предполагать и это ограничение нужно явно сообщить пользователю. Exact `DocumentStore.head`/`listMetadata` сначала получают logical metadata с canonical-over-legacy precedence; output/size/scan gates выполняются до body read. Полный допустимый объект всё ещё скачивается целиком, но один turn физически ограничен per-document 256 KiB и суммарными 2 MiB.
- `/proc/thread` двухслойный: сначала `thread_summary` (≤4 000 chars для exact production-rendered section: heading, watermark, notice, XML wrapper и escaped checkpoint), затем до 10 свежих completed turns (≤12 000 chars для exact rendered history section с heading, notice, XML wrappers, escaping и truncation marker). Projection принимает сохранённый checkpoint только если этот exact renderer укладывается в ceiling; legacy/повреждённый oversized checkpoint пропускается, не блокируя recent history и не удаляя raw turns. Projection сохраняет contiguous newest suffix; поля сначала ограничиваются обычным per-field ceiling, а если один newest turn всё ещё не помещается после escaping, оба поля детерминированно дополнительно сокращаются по Unicode code points до fit без over-ceiling секции. После durable append ответа асинхронная job детерминированно выбирает oldest pending turns вне recent-window: один запуск читает не более 10 turns после watermark и делает ровно один summarizer call для непустого batch. Поля user/assistant ограничены отдельным compaction input ceiling (по умолчанию 2 000 chars на поле), а provider получает консервативный `modelSettings.maxOutputTokens`, рассчитанный из character ceiling; исполнимой границей остаётся последующая проверка exact rendered Unicode characters. Сначала валидируются четыре обязательные секции. Если канонический structured result не помещается после escaping, application без второго provider call детерминированно сохраняет все headings, добавляет под «Факты» marker `- История сокращена для лимита.` и сокращает тела секций по Unicode code points, каждый candidate измеряя тем же production renderer с фактическим watermark. Минимальный конфиг `threadSummaryCharacters` обязан вмещать exact rendered headings, marker и canonical watermark shape и валидируется при старте. Неструктурированный result не сохраняется. Compaction не запускает insight extraction и не имеет durable write-capabilities кроме `ThreadSummaryStore`; insights создаются только обычным agent-led typed process. Summarizer получает только предыдущий checkpoint + bounded batch и не имеет write-портов. Previous checkpoint передаётся после единственного trusted heading и короткого notice только внутри `<untrusted-previous-checkpoint>`: содержимое ограничивается summary ceiling по Unicode code points, затем экранирует `&`, `<`, `>` и нейтрализует line-leading Markdown headings; поэтому checkpoint не может закрыть container, создать prompt-level section или подменить trusted heading newly expired turns. Watermark — inclusive диапазон `fromMessageId..throughMessageId`; он продвигается на конец сохранённого batch только после успешного summary save. При сбое остаётся предыдущий валидный checkpoint и существующий history truncation marker. `ConversationStore` и `DocumentStore` не изменяются компакшном: raw turns остаются каноническими и summary можно регенерировать по watermark.
- `/proc/profile` владеет подтверждёнными structured operational fields. `90_agent_memory/soul.md` и legacy `persona.md` — только untrusted prose preferences; при конфликте они не переопределяют profile, policy или capabilities.
- `/run/actions` не включается в каждый запрос и не может менять роль, policy, process selection или capability set; его подключают только для явной диагностики или recovery.
- Typed tools передаются отдельно; system context не содержит store credentials, transport ids, signed URLs или shell/file access.

## Решение по ingestion-суммаризации

Исходная идея `prs-jxy.4` — LLM-суммаризация документов при ingestion — **отклонена**. Она добавляет сетевую зависимость и недетерминированный производный текст, ломает executable specs без LLM/сети и создаёт второй источник drift рядом с оригиналом. Её роль выполняет tiered index: metadata-only machine index гарантирует полную структурную карту, а owner/agent-authored `INDEX.md` хранит компактную устойчивую семантическую аннотацию.

## Состояние после C.0 и следующие задачи

Product chat следует agent-led routing и owner isolation, включает `/proc/profile`, приоритетный core `/proc/context`, machine index, `/proc/records`, optional incremental `thread_summary` и bounded recent history. `/proc/inbox` и `/run/actions` пока отсутствуют. Единственный product chat-path сохраняется.

Следующий этап `prs-mcn` расширяет существующий `/proc/records` bounded-проекцией задач и добавляет только request-scoped typed task capabilities за explicit confirmation boundary. Новый ambient source, pre-flight router или обязательная календарная интеграция не вводятся. `readProcess(id)` (`prs-jxy.8`) остаётся deferred до 5+ активных процессов или приближения assistant manual к configured source ceiling.
