# RFC: инвентарь рутин и быстрые победы как результат «Минутки»

## Status

**proposed (2026-09-03).** RFC фиксирует границу результата бесплатного двухнедельного этапа «Минутки»: отчёт компании и личный отчёт сотрудника описывают **рутины и быстрые улучшения**, а не бизнес-процессы. Полноценное обследование процессов выносится в отдельный платный этап и в runtime этого репозитория не строится. Документ заменяет [RFC бизнес-процессов и каталога автоматизации](./rfc-business-process-discovery-and-automation-catalog.md).

## 1. Проблема

### 1.1. Два этапа смешаны в один продукт

Продуктовая линейка состоит из двух разных этапов:

| Этап | Формат | Цена | Данные | Результат |
| --- | --- | --- | --- | --- |
| **1. «Минутка»** | дополнение к курсу: один короткий опрос в день, две недели | бесплатно | самоотчёт сотрудника вечером, ≤1 уточняющий вопрос | на что уходит время, какие рутины повторяются, что нудно, что можно быстро упростить |
| **2. Обследование** | интервью, разбор регламентов и систем, проектирование агентов и интеграций | платно | process interviews, документы, доступ к системам | карта бизнес-процессов, проект автоматизации, план внедрения |

Данные первого этапа физически не позволяют описать бизнес-процесс: сотрудник в одном сообщении называет, чем занимался, а не trigger, вход/выход, шаги, handoffs и cycle time. Попытка вытянуть это из вечернего касания даёт один из двух исходов: либо агент мучает сотрудника расспросами (нарушает [ритм](./rfc-minutka-daily-rhythm.md) и роняет response rate), либо поля остаются пустыми и «карта процессов» оказывается фикцией.

[Superseded RFC](./rfc-business-process-discovery-and-automation-catalog.md) проектирует именно второй этап поверх данных первого: `ProcessEpisode` с ~25 полями, кластеризацию в `BusinessProcessCandidate`, версионируемый `BusinessProcess`, глобальный `AutomationCaseCatalog` из 17 полей, четыре оси confidence, четыре новые research-таблицы, merge/split review и progressive process interview. Это стоимость платного обследования, вложенная в бесплатный продукт.

### 1.2. Что действительно не хватает текущему отчёту

Canonical activity ([`src/contracts/minutka-activity.ts`](../../src/contracts/minutka-activity.ts)) хранит шесть закрытых facets и **ни одного слова о том, что именно делал сотрудник**. Поэтому:

- `CompanyReportingService` группирует по `taskCategory + routinePattern` и называет «процессом» пару `admin + manual_reporting`;
- личный отчёт (`cycle-activity-summary.ts`) сообщает «повторилась категория reporting», а не «шесть раз за две недели — сверка остатков в 1С с таблицей»;
- время нигде не суммируется: `durationBucket` только перечисляется, хотя «на что уходит время» — главный вопрос первого этапа;
- «быстрая победа» не формулируется: `automationOption` — общая фраза про «стандартизировать шаги».

Misfit по [планке качества](./rfc-pilot-quality-bar.md): baseline §2 обещает компании «карту процессов, 30/60/90 план» за бесплатный этап, а contract activity не даёт данных даже для названия рутины. Решение — не расширять данные до процесса, а сузить обещание до рутины и добавить в activity ровно то, чего не хватает для названия и времени.

## 2. Решение

### 2.1. Граница результата первого этапа

«Минутка» отвечает на четыре вопроса и только на них:

1. **Куда уходит время** группы по категориям работы и по конкретным рутинам (порядок величины, часы за цикл).
2. **Что повторяется** — рутины, названные самими сотрудниками, с частотой и числом contributors.
3. **Что нудно или мешает** — рутины с явными сигналами трения и энергии.
4. **Что можно быстро упростить** — быстрая победа из закрытого каталога с оценкой усилий и первым шагом.

Всё, что требует знания устройства процесса (шаги, handoffs, data flow, cycle time, prerequisites интеграции, 30/60/90 с owner и exit criteria), выходит в раздел отчёта **«Для углублённого обследования»** — это явный мостик к платному этапу, а не обещание первого.

### 2.2. Ubiquitous language

| Понятие | Значение |
| --- | --- |
| `Activity` | Фактическая единица работы, названная сотрудником (без изменений) |
| `routineLabel` | Короткое название работы словами сотрудника, поле activity |
| `Routine` | Группа activities с одинаковым нормализованным `routineLabel` внутри группы; derived read model отчёта, не хранится |
| `QuickWin` | Строка закрытого каталога быстрых улучшений, сопоставленная рутине детерминированно по facets |
| `Deep-dive candidate` | Рутина, для которой быстрой победы нет или evidence слабый; передаётся во второй этап как вопрос |

Термин `business process` в первом этапе не используется. `AssistantProcess` (`evening_reflection` и др.) остаётся runtime-понятием агента.

### 2.3. Два новых поля activity

В `activityCollectionItemSchema` добавляются два optional поля; всё остальное в контракте, extractor и store не меняется.

```ts
routineLabel: z.string().trim().min(3).max(80).optional()
  // Короткое название работы словами сотрудника: «сверка остатков 1С с таблицей»,
  // «подготовка КП по заявке», «согласование графика доставки».
  // Без имён людей, клиентов и контрагентов, без сумм, номеров и ссылок.
  // Omit, если сотрудник назвал только категорию («работал с почтой» → category, без label).

recurrence: z.enum(["daily", "several_per_week", "weekly", "monthly", "one_off"]).optional()
  // Только если сотрудник явно назвал частоту («каждый день», «по пятницам», «раз в месяц»).
  // Не выводится из повторов в истории; повторяемость считает отчёт.
```

Правила:

1. `routineLabel` — **факт**, как и остальные facets: это то, как сотрудник назвал работу, а не интерпретация. Именно поэтому поле живёт в activity, а не в derived слое. Отвергнутый в superseded RFC вариант «все process fields в `Activity`» здесь не воспроизводится: добавляются название и заявленная частота, а не trigger/steps/handoffs.
2. Поле хранится в `minutka_private.activities` (миграция: две nullable колонки) и участвует в revisions/corrections/supersession по существующим правилам; отдельного purge не нужно.
3. Extractor получает правило в манифесте `evening_reflection` (и в общем activity rule `AGENTS.md`): label ≤80 символов, именная группа, без персональных данных; при сомнении — omit. Existing `needs_clarification` не расширяется: отсутствие label не является поводом для вопроса.
4. Клиентский DTO не показывает raw label автоматически: в клиентский отчёт попадает `routine.name` — самый частый вариант label после применения alias-ов (§2.4). Перед передачей он проходит boundary preflight (§2.8): код флагует подозрительное содержимое, методолог подтверждает или правит label существующим correction path.

### 2.4. Группировка в рутины — без кластеризации

`Routine` вычисляется в `CompanyReportingService` на каждом запуске из активных activities scope:

```text
routineKey = lower(trim(collapseWhitespace(stripPunctuation(routineLabel))))
```

Внутри `(companyId, groupId)` activities с одним `routineKey` образуют рутину. Рутина несёт:

- `name` — самый частый исходный label; `variants` — остальные варианты написания (только internal DTO);
- `contributors`, `observations`, `activeDates` и `confidence` по действующей policy §2.9 родительского RFC;
- `statedRecurrence` — распределение `recurrence`, если сотрудники его называли; показывается как заявлено и не сверяется с наблюдёнными повторами: отчёт строится на самоотчёте сотрудника (решение оператора, §8);
- `systems`, `taskCategories`;
- `estimatedHours` (§2.5);
- `frictionSignals`, `energySignals` (§2.6);
- `quickWin` (§2.7) или `deepDive: true`;
- `evidenceRefs` (только internal).

Activities без `routineLabel` остаются в существующих buckets `taskCategory + routinePattern` и входят в бюджет времени по категории; рутиной они не становятся.

**Синонимы.** Нормализация не склеит «сверка остатков», «сверял остатки в 1С» и «остатки сверить с таблицей»: на группе из девяти человек с разной манерой речи это раздробит рутины и обесценит топ по часам. Склейку делает LLM, но не внутри пути отчёта, а отдельным подготовительным шагом с проверяемым результатом:

1. Typed operator-команда `routine-aliases suggest --company <id> --group <id>` берёт список различных `routineKey` группы (без subject keys, сообщений и PII по правилу extractor), просит модель сгруппировать синонимы и назвать каждую группу одним каноническим именем и пишет файл `routine-aliases.<company>.<group>.json` вида `{ "сверял остатки в 1с": "сверка остатков 1с с таблицей" }` с пометкой `suggestedBy: <model@version>`.
2. Методолог проверяет и правит файл: это проверка, а не составление. Файл лежит в операторском контуре, версионируется вместе с отчётом и не пишется в БД.
3. Команда отчёта принимает файл флагом `--aliases` и применяет его до группировки детерминированно: одни и те же activities и один и тот же файл дают один и тот же отчёт на каждом recompute.

`variants` в internal DTO показывает, что именно склеилось. LLM-кластеризация внутри `CompanyReportingService`, `candidate` entities, merge/split и review-таблицы не вводятся: путь отчёта остаётся без сети и воспроизводимым, а результат модели становится проверенным артефактом до того, как попадёт в отчёт. Маркировку самих activities (label, facets) модель уже делает в extractor; спорна только склейка между людьми, и она решена выше.

### 2.5. Бюджет времени

Первый этап отвечает «на что уходит время» порядком величины. `durationBucket` переводится в часы по фиксированной таблице:

| bucket | часы |
| --- | --- |
| `lt_15m` | 0.2 |
| `15_30m` | 0.4 |
| `30_60m` | 0.75 |
| `1_2h` | 1.5 |
| `2_4h` | 3 |
| `gt_4h` | 5 |

`estimatedHours` рутины и категории — сумма по activities с известным bucket; число activities без bucket показывается отдельно (`unsizedObservations`). В отчёте величина подписана как «≈ часов за цикл по самоотчётам группы», а не как замер. Доля категории считается от суммы известных часов. Точность не улучшается дополнительными вопросами: если сотрудник не назвал длительность, она отсутствует.

### 2.6. Сигналы трения и нудности

Никаких новых facets. Рутина получает:

- `frictionSignals` — число activities с `routinePattern ∈ {manual_reporting, coordination_overhead, context_switching, waiting_for_input, meeting_overload, unclear_priority}` и распределение по значениям;
- `energySignals` — число activities с `energyStressMarker ∈ {frustration, fatigue, overload, focus_loss, blocked_progress}`;
- `automationHypotheses` — распределение `automationCandidate` (как сейчас в `supportingEvidence`).

Ранжирование в отчёте — две отдельные шкалы, без составного score: «куда уходит время» сортирует по `estimatedHours`, «что мешает» — по `frictionSignals + energySignals`. Сотрудник не оценивается: сигнал агрегирован по рутине и показывается только при `contributors ≥ 2` либо как `hypothesis` без привязки к должности, если contributor один (действующее правило rare-role).

### 2.7. Каталог быстрых побед

Вместо `AutomationCaseCatalog` (17 полей, semantic matching, четыре исхода) вводится закрытая таблица `quickWinCatalog` в коде (`src/application/quick-wins.ts`), ~10 строк, детерминированное сопоставление по facets рутины. Строка каталога:

```ts
type QuickWin = {
  id: string;                     // "report_template", "status_bot", ...
  matches: {                      // рутина подходит, если совпал хотя бы один automationCandidate
    automationCandidates?: AutomationCandidateType[];   // ИЛИ хотя бы один routinePattern
    routinePatterns?: RoutinePatternType[];
  };
  title: string;                  // «Шаблон отчёта с формулами и AI-черновиком текста»
  whatChanges: string;            // одно предложение: что перестаёт делаться вручную
  effort: "hours" | "days" | "weeks";
  whoCanDo: "employee" | "internal_it" | "with_algoritm";
  humanInTheLoop: string;         // что остаётся за человеком
  firstStep: string;              // одно действие на следующую неделю
};
```

Стартовый состав — девять строк (решение оператора, §8); уточняется первым циклом, не RFC:

| id | триггер | суть |
| --- | --- | --- |
| `report_template` | `report_generation`, `manual_reporting` | шаблон + формулы/сводная; AI-черновик текста по данным |
| `data_import_export` | `data_entry_reduction` + `spreadsheets`/`crm`/`one_c` | импорт/экспорт вместо ручного переноса; форма ввода |
| `async_status` | `async_status_update`, `meeting_overload` | письменный статус вместо встречи; статус-бот в мессенджере |
| `checklist` | `template_or_checklist` | чек-лист/шаблон повторяющейся операции |
| `routing_rule` | `task_routing`, `coordination_overhead` | одна точка входа и правило маршрутизации |
| `waiting_sla` | `waiting_for_input` | напоминание/эскалация по сроку ожидания |
| `batching` | `context_switching` | пакетирование однотипных задач, окна без прерываний |
| `mail_extraction` | `data_entry_reduction` + `email` | AI-ассистент извлечения реквизитов из писем с проверкой |
| `priority_rule` | `unclear_priority` | явное правило приоритета на неделю |

Если ни одна строка не совпала, либо `automationCandidate = other`, либо рутина в топе по часам без сигналов — рутина помечается `deepDive: true` и уходит в раздел «Для углублённого обследования». Каталог не является evidence компании и не меняет confidence.

### 2.8. Отчёт компании: «Карта рутин и быстрых улучшений»

Клиентский DTO `minutka-client-report.v2`:

```text
1. Coverage и ограничения           — как сейчас
2. Куда уходит время                — таблица по taskCategory: ≈часов, доля, contributors
3. Топ рутин по времени (≤10)       — name, scope, contributors/observations/dates, ≈часов,
                                      systems, statedRecurrence, confidence,
                                      quickWin {title, whatChanges, effort, whoCanDo,
                                      humanInTheLoop, firstStep} | deepDive
4. Что мешает и раздражает (≤5)     — рутины по сигналам трения/энергии + quickWin
5. С чего начать на следующей неделе — ≤3 firstStep из п.3–4, отсортированных по effort
6. Для углублённого обследования    — deep-dive рутины и вопросы к ним (мост ко второму этапу)
7. Чего нельзя заключить из этих данных
```

Из клиентской рекомендации уходят `prerequisites`, `risks`, `expectedEffect` и 30/60/90 план: они требуют знания процесса, которого у первого этапа нет. На их месте — `effort`, `whoCanDo` и `firstStep`. Confidence policy, границы клиентского DTO (запрещённые поля §3.1 шаблона) и ручной review/publish flow §6 шаблона не меняются.

**Boundary preflight: код флагует, человек подтверждает.** Сегодня шаг 5 flow §6 шаблона — ручной чек-лист: запрещённые поля и содержимое из §3.1 (ключи участников и contributors, IDs, raw-сообщения и цитаты, trace IDs, research notes, оценки конкретного человека, сочетания редких идентифицирующих деталей), корректность coverage/confidence, наличие human-in-the-loop. Структурную часть закрывает схема клиентского DTO. `routine.name` — первое свободно-текстовое поле, идущее от слов сотрудника в отчёт компании, поэтому содержательную часть берёт на себя команда отчёта и выдаёт в internal DTO `preflightFindings[]` (`{ field, routineKey, rule, excerpt, severity }`):

- детерминированный lint свободного текста (`routine.name`, `variants`): пары заглавных слов и суффиксы отчеств, ООО/ИП/АО, цифровые последовательности от четырёх знаков, валюта и суммы, e-mail, URL, @-хэндлы, кавычки-цитаты;
- LLM-проверка вторым слоем на идентифицирующие детали, которые regex не ловит («единственный менеджер по Казахстану»): ответ только `ok` или `flag` с причиной, текст не переписывается;
- assertions действующей policy: rare-role (`contributors < 2` → `hypothesis` без должности), пороги confidence, coverage — они уже считаются кодом и проверяются, а не пересчитываются вручную.

Ничего не вырезается автоматически: методолог читает список находок вместо всего отчёта, правит label существующим correction path и пересчитывает отчёт. Ручными остаются шаги 6–9 flow (редактура, решение о передаче, публикация, audit).

Internal DTO `minutka-internal-report/v2` добавляет `routines[]` с `variants`, `evidenceRefs`, `subjectKey`-агрегатами и оставляет существующие buckets.

### 2.9. Личный отчёт сотрудника

`readWeeklyActivities` и `readCycleActivities` дополняются `routines[]` того же вида (owner-scoped, без данных других сотрудников, без research IDs). Манифесты `weekly_summary` и `final_report`:

- называют рутины словами сотрудника и частотой: «за две недели шесть раз — сверка остатков 1С с таблицей»; ≈часы сотруднику не показываются (решение оператора, §8: риск самооценки), личный `routines[]` не несёт `estimatedHours`;
- паттерном по-прежнему считается только повторившееся ≥2 раз (правило `cyclePatternMinimumCount` распространяется на рутины);
- в `final_report` два-три шага упрощения берутся из `quickWin.firstStep` подходящих рутин, где `whoCanDo = employee`;
- `weekly_summary` предлагает подтвердить или поправить топ-3 рутины словами; исправление идёт существующим `repair`-путём activity, отдельного хранилища подтверждений нет.

### 2.10. Диалог не меняется

Число касаний и вопросов остаётся как в [RFC ритма](./rfc-minutka-daily-rhythm.md). Меняется одна фраза вечернего приглашения: «назовите работу своими словами и, если знаете, сколько заняла и как часто повторяется». Progressive enrichment, приоритет уточняющих вопросов и отдельный process interview из superseded RFC не вводятся.

### Ограничения и принципы

1. **Factual boundary.** `routineLabel`/`recurrence` — то, что сказал сотрудник; интерпретация (группировка, часы, quick win) живёт только в read model отчёта и пересчитывается на каждом запуске.
2. **Нет новых stores.** Ни одной новой таблицы; два nullable столбца в `activities`; alias-файл — операторский артефакт.
3. **Client boundary без изменений.** Raw labels, variants, evidenceRefs, subject keys — только internal DTO.
4. **Не оценивать человека.** Часы и сигналы агрегируются по рутине и группе; рутина одного contributor — `hypothesis` без привязки к должности.
5. **Порядок величины честно назван.** ≈часы подписаны как самоотчёт, без «ROI» и «экономии N часов в год».
6. **Мост, а не обещание.** Всё, что требует обследования, попадает в «Для углублённого обследования», а не в рекомендации.
7. **LLM там, где его результат проверяется и версионируется.** Маркировку activities (extractor) и склейку синонимов (`routine-aliases suggest`) делает модель; путь отчёта детерминирован и работает без сети: одни и те же activities и alias-файл дают один и тот же отчёт. Таблица quick wins в коде до каталога с matching.

## 5. Trade-offs

**Получаем:**

- отчёт называет конкретные рутины словами сотрудников и отвечает «куда уходит время» уже на первом цикле;
- ноль новых stores, один pass extractor, без review-lifecycle и кластеризации;
- диалог не тяжелеет: тот же ритм, тот же ≤1 вопрос;
- честная граница между бесплатным и платным этапом, встроенная в структуру отчёта («Для углублённого обследования» как лид);
- accumulated corpus остаётся пригодным для второго этапа: messages и traces уже хранят всё, что понадобится обследованию.

**Принимаем:**

- free-text поле в activity: риск персональных данных в label закрывается правилом extractor и preflight lint с ручным подтверждением, а не схемой;
- синонимы склеиваются через alias-файл: модель предлагает, методолог проверяет; без файла отчёт показывает синонимы отдельными рутинами;
- ≈часы — грубая оценка по bucket-ам, не замер;
- quick win из таблицы по facets будет иногда неточен; методолог правит на review, как сейчас правит `automationOption`.

**Отвергнуто:**

- *Derived process layer из superseded RFC* — стоимость и UX платного обследования в бесплатном продукте; данные первого этапа его не наполняют.
- *Ничего не менять в activity, а рутины выделять методологу из messages вручную* — не масштабируется даже на семь участников × 14 дней и не даёт личному отчёту назвать рутину.
- *LLM-кластеризация labels внутри команды отчёта* — недетерминированный результат на каждом recompute, сеть в пути отчёта, specs без LLM перестают его покрывать. Вместо этого модель предлагает alias-файл (§2.4), а отчёт применяет его детерминированно.
- *Свободный текст `quickWin` от модели* — теряет проверяемость; закрытая таблица правится как код.

## 6. Error handling & деградация

- **Label не извлечён.** Activity сохраняется с facets, попадает в бюджет времени по категории; рутиной не становится; в отчёте — строка «без названия» только в internal DTO.
- **Label содержит имя/контрагента.** Extractor-правило нарушено; ловится boundary preflight методолога; исправление — существующий correction path activity, затем пересчёт отчёта. В клиентский DTO raw label не попадает автоматически.
- **Нет `durationBucket`.** Рутина показывает `unsizedObservations`; часы не домысливаются.
- **Alias-файл не той группы или с циклом.** Команда отчёта прекращается целиком с явной ошибкой; отчёт без alias-ов остаётся доступен.
- **Провайдер недоступен для `routine-aliases suggest`.** Команда завершается ошибкой без файла; ранее проверенный файл и отчёт без alias-ов остаются доступны.
- **Ложное срабатывание preflight lint.** Находка помечается методологом как проверенная в операторском контуре; отчёт не блокируется, текст не меняется.
- **Quick win не совпал.** Рутина уходит в «Для углублённого обследования»; confidence и evidence не меняются.
- **Correction/purge.** Report path перечитывает canonical activities на каждом запуске (как сейчас); derived state отсутствует, инвалидировать нечего.
- **Мало данных.** Действующие пороги `sufficientData` и `insufficient` coverage; рутины не называются паттерном при `< 2` повторов.

## 7. Не-цели и когда пересмотреть

Не входит в первый этап:

- описание бизнес-процессов (trigger, шаги, handoffs, data flow, cycle time);
- process interviews и любой третий вопрос в день;
- AutomationCase catalog с semantic matching и vector DB;
- LLM-кластеризация рутин и review-lifecycle (merge/split/candidate);
- 30/60/90 план, prerequisites интеграций, оценка ROI;
- новые research-таблицы и derived stores;
- backfill старых активностей.

Пересмотреть:

- **Переиспользование labels группы в extractor** (модель видит существующие `routineKey` группы и переиспользует подходящий при извлечении: сходимость до конца цикла и в личном отчёте) — когда методолог правит предложенный alias-файл живой группы более чем на ~30% строк или личный отчёт не сходится без alias-ов. Риск — слова других сотрудников в контексте агента одного, поэтому не в первый цикл.
- **Модель процесса второго этапа** — когда есть оплаченное обследование и методологу нужна машинная поддержка (тогда superseded RFC — стартовая точка, но в отдельном контуре, а не в daily runtime).
- **Дополнительное поле activity** (например, `workObject`) — только по зафиксированному misfit живого цикла: рутина не различима без него.
- **Точность часов** — если компания просит baseline для платного этапа; тогда замер делает обследование, а не вечерний опрос.

## 8. Решения оператора и открытые вопросы

Решения оператора (2026-09-04):

1. Рутина одного contributor в клиентском отчёте — `hypothesis` без привязки к должности (как сейчас).
2. `statedRecurrence` показывается компании как заявлено, даже если противоречит наблюдённым повторам: отчёт строится на самоотчёте сотрудника и доверии к нему.
3. Стартовый состав `quickWinCatalog` — девять строк §2.7.
4. Личный отчёт показывает по рутинам только частоту, без ≈часов.

Открытые вопросы (закрываются спайками §9):

1. Нужен ли alias-файл уже в первом цикле или достаточно `variants` в internal DTO — отвечает спайк 2 метрикой покрытия топ-10 без alias-ов.
2. Должна ли команда отчёта отказывать в client DTO при непросмотренных `preflightFindings` с `severity = high`, или findings только информируют — решается после спайка 3 по числу и качеству находок.
