🏠 Обзор проекта

📋 Что такое «Минутка»?

«Минутка» — AI-партнёр для сотрудников в рамках корпоративной программы обучения AI от команды «Алгоритм». В течение двухнедельного цикла сотрудник общается с Минуткой через Telegram: планирует день утром, при желании сверяется днём, рефлексирует вечером — и получает персонализированную обратную связь о паттернах работы, энергии и фокусе.

Сегодня это единый runtime: один Node.js-процесс обслуживает Telegram polling shell и аутентифицированный HTTP API (/v1), поверх которого работает standalone CLI — для пилотных сотрудников и администрирования. Состояние живёт в PostgreSQL и переживает перезапуски.

📲 Сценарий 1 — Вход в программу через Telegram

Сотрудник получает индивидуальную ссылку-инвайт и открывает бота командой /start <код>. Бот показывает условия приватности с inline-кнопками согласия; consent привязывается к Telegram-аккаунту атомарно — состояние сессии и согласие сохраняются одной транзакцией. Затем короткий онбординг: роль, типичные задачи, персона общения («Поддержка» / «Эффективность»), уровень знакомства с AI и желаемая длина ответов.

💬 Сценарий 2 — Ежедневный диалог: план утром, рефлексия вечером

Сотрудник пишет обычные текстовые сообщения. Пока агент думает, бот показывает статус «печатает…»; длинные ответы автоматически режутся на части под лимит Telegram. Decision router распознаёт смысл сообщения: утренний план сохраняется в контекст треда, а вечерняя рефлексия сверяется с утренним планом — Минутка отражает факты без оценок, называет 1–2 паттерна (перегруз звонками, context switching) и предлагает один шаг на завтра. Follow-up-вопросы («а что я говорил утром?») разрешаются из недавнего контекста беседы.

🖥 Сценарий 6 — Тот же диалог из CLI (cross-channel)

Сотрудник (или инженер в пилоте) может продолжить разговор из терминала: CLI — отдельный OS-процесс, который ходит в тот же живой runtime по HTTP с bearer-токеном. Личность выводится из токена, а не из аргументов; указав Telegram thread ID, можно продолжить именно тот тред, что вёлся в боте.

# токен сотрудника определяет identity $ export MINUTKA_API_URL=http://127.0.0.1:8787 $ export MINUTKA_API_TOKEN=<employee-token> $ npm run cli -- employee chat --thread workday-1 --text 'План на сегодня' $ npm run cli -- employee profile $ npm run cli -- employee insights --kind automation_candidate

С Phase 4.1 это реальная директория vault/ в git. Динамическая часть (/proc) рендерится в контекст из typed runtime projections с ограниченными scope и лимитами чтения; сырые данные stores в контекст агента не попадают.

⚙️ Бизнес-процессы агента (Agent Vault)

📖 Концепция Agent Vault

Поведение MinutkaAgent управляется не одним гигантским system prompt, а набором атомарных бизнес-процессов в Markdown под git (директория vault/processes/). Каждый процесс — procedural playbook с чёткими секциями: когда применяется, входы, шаги, выходы, privacy-ноты, anti-patterns и dependencies.

Маршрутизация: SO-CoT Constrained Decision Router выбирает процессы по смыслу, а не по ключевым словам.

Когда: Первый ответ после завершения профиля и принятия consent.

Что делает: Подтверждает получение профиля, объясняет роль Минутки, приглашает к первому действию. Применяет выбранную персону.

Anti-patterns: длинные курсы по AI, давление на участие, оценка продуктивности.

readonlyPhase 3.5

Когда: Вопросы о приватности, данных компании, методологе, удалении данных.

Что делает: Отвечает на вопросы о видимости данных. Отделён от guardrails и insight extraction.

Anti-patterns: смешивание privacy-ответа с рабочей рефлексией.

readonlyPhase 3.5

Когда: Разбор дня: итоги, блокеры, встречи/звонки, усталость, сравнение с утренним планом.

Что делает: Ищет утренний план в контексте. Отражает факты без оценки. Называет 1–2 паттерна: перегруз звонками, context switching, blocked progress. Предлагает один шаг на завтра.

Anti-patterns: «Ты не выполнил план», «Твоя продуктивность низкая», лекции по тайм-менеджменту.

readonlyPhase 3.5

Когда: Запрос на написание контента, ресерч, обучение AI, нерелевантная тема или попытка обхода ограничений.

Что делает: Мягко отказывает и возвращает к рабочей тематике. Основной агент не вызывается.

Anti-patterns: жёсткий отказ, копирование правил из system prompt, скрытое разрешение нерелевантного запроса.

readonlyPhase 3.5

Когда: Decision router отмечает сообщение как insight candidate после substantive workday reflection.

Что делает: Извлекает структурированные сигналы: категории задач, рутина, энергия/стресс, automation candidates. Сохраняет privacy-safe insights.

🧪 Принцип: Specs без внешних API

Все executable specs работают через mock runners и tools — без реального LLM, Telegram API или STT. Это обеспечивает детерминированные, быстрые и надёжные тесты. Отдельно существует persistence-контракт (specs/persistence/postgres-contract.spec.ts), который гоняется против реального PostgreSQL через npm run verify:persistence.

🔒 Приватность и границы

🛡 Ключевые принципы

  • Диалог сотрудника = личный контекст, не доступен компании
  • Компания получает только обезличенные агрегаты
  • Минимальная группа для аналитики: ≥5 сотрудников
  • ФИО и телефон маскируются до отправки в AI-провайдеры
  • Методолог НЕ видит транскрипты, задачи и эмоции отдельных людей
  • Сотрудник может удалить все свои данные одним действием
  • Raw transcripts не сохраняются в insights
  • Privacy-safe employeeId (псевдоним, не PII)

🟢 Что видит сотрудник

  • Свой полный диалог с Минуткой
  • Свой портрет и профиль (раздел «Я»)
  • Персональные недельные и финальные отчёты
  • Выбранная персона и настройки
  • Кнопка удаления всех данных

🔴 Что НЕ видят компания и методолог

  • ❌ Транскрипты голосовых сообщений
  • ❌ Конкретные задачи отдельных людей
  • ❌ Эмоциональное состояние конкретного сотрудника
  • ❌ Имена в ответах и рефлексиях
  • ❌ Срезы меньше 5 человек

# 1. PostgreSQL (локально — через Docker Compose) и миграции $ docker compose up -d $ npm run db:migrate $ npm run db:status # 2. .env: DATABASE_URL, peppers и токены (openssl rand -hex 32) MINUTKA_API_HOST=127.0.0.1 MINUTKA_API_PORT=8787 MINUTKA_ADMIN_TOKEN=<token> MINUTKA_SERVICE_TOKEN=<token> MINUTKA_EMPLOYEE_TOKENS=emp_pilot:<token> # 3. Listener по умолчанию слушает только loopback; не-loopback деплой требует MINUTKA_API_ALLOW_NON_LOOPBACK + MINUTKA_API_TRUST_PROXY и TLS-терминирующего reverse proxy. GET /healthz — без аутентификации.

🖥 Администрирование через CLI

CLI (npm run cli) — отдельный процесс: он никогда не создаёт runtime и не ходит в PostgreSQL напрямую, только по HTTP с bearer-токеном. Роль определяется токеном: employee-токен даёт команды employee * от имени этого сотрудника, admin-токен — привилегированные admin *.

$ export MINUTKA_API_URL=http://127.0.0.1:8787 $ export MINUTKA_API_TOKEN=<token> # Оператор (admin-токен): выпуск инвайта $ npm run cli -- admin issue-invite --employee emp_pilot --invite <code> # Сотрудник (employee-токен): полный цикл $ npm run cli -- employee open-invite --invite <code> $ npm run cli -- employee accept-consent --yes $ npm run cli -- employee complete-onboarding --role "аналитик" \ --task "отчёты" --persona support --ai-level beginner $ npm run cli -- employee profile $ npm run cli -- employee chat --thread workday-1 --text "План на сегодня" $ npm run cli -- employee insights --kind routine_pattern $ npm run cli -- employee feedback --target-message <id> --rating positive

🔧 Инженерные правила проекта

  • Не ломать слои: Telegram handler не бизнес-слой
  • Specs без внешних API: LLM/Telegram мокируются
  • Mastra docs-first: сверяться с embedded docs перед API
  • Provider registry first: проверять модель перед использованием
  • Privacy by structure: сначала domain types, потом отчёты
  • Business processes as code: process-файлы в git
  • Минимальные коммиты по фазам: зелёный verify → тег
  • Unix-like namespace как контракт агента
