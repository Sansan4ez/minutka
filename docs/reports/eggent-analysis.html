Eggent × personal-assistant

исследование · 23 июля 2026

Сравнительный анализ репозитория /home/admin/eggent (v0.2.0, MIT) и нашего прототипа персонального ассистента: как проекты соотносятся, где дополняют друг друга и что стоит позаимствовать.

Короткий ответ на четыре вопроса

1 · СООТНОШЕНИЕ
Соседи, а не конкуренты

Оба — single-owner ассистенты с Telegram, но противоположные философии: Eggent — универсальный «AI-workspace» с широкими правами агента; наш проект — узкий ассистент с типизированными границами, аудитом и подтверждениями.

2 · ВМЕСТЕ?
Да — как дополнение рекомендовано

Лаборатория процессов и исполнитель «тяжёлых» неперсональных задач через External API. Сливать в один продукт не стоит: модели безопасности несовместимы.

3 · ЧТО ВЗЯТЬ
12 идей, 4 быстрых

Главное: локальный STT на whisper.cpp (вместо облачного), HTML-форматирование в Telegram, staged-прогресс, загрузчики документов, паттерны pipelines и планировщика.

4 · ВАЖНОЕ
Живой, но «двухслойный»

Проект активен (релиз 0.2.0 — 22 июля 2026), MIT. Внутри — двойной рантайм (legacy + pi SDK), файловые сторы без БД, планировщик не переживает рестарт. Брать паттерны, не код.

Что такое Eggent

Браузерный «local-first AI workspace»: каждый проект — это каталог-агент со своими инструкциями (context.md), памятью (memory.md), скиллами, MCP-конфигом и моделью. Поверх — веб-дашборд, чат, Telegram-бот, пайплайны из нескольких агентов, планировщик, External API и локальная транскрипция голоса. Агентское ядро — сторонний рантайм pi-coding-agent (сессии, инструменты, скиллы, субагенты, расписания), Eggent — тонкий мост над ним.

Web-чат / Telegram / External API
→
Next.js API-роуты
→
pi-сессия (agent + bash + файлы + MCP + скиллы)
→
data/ (файлы, JSON)

Агент действует внутри доверенной песочницы владельца: bash, файлы, выполнение кода, установка пакетов. Ограничений на действия и аудита нет — безопасность строится на том, что весь контур принадлежит одному пользователю.

Чем это отличается от нашей модели

Telegram / HTTP / CLI
→
AssistantService
→
typed use-cases + подтверждения
→
PostgreSQL / MinIO + аудит

У нас агент никогда не пишет в хранилища напрямую и не выполняет внешние действия без подтверждения: только типизированные инструменты, у которых обработчик — это use-case с привязкой userId и записью в аудит. Контекст собирается бюджетированными проекциями /proc/*, а вся логика проверяется executable-спеками без LLM и сети. Это принципиально другой уровень гарантий — и именно он не позволяет просто «взять Eggent как основу».

Итог: Eggent выигрывает в широте продукта (UI, планировщик, пайплайны, MCP, локальный голос), наш проект — в строгости фундамента (границы, аудит, БД, спеки, приватность). Это и есть причина, почему они дополняют, а не заменяют друг друга.

Можно ли использовать вместе?

Да — но по ролям, с жёсткой границей по данным. Выберите сценарий, чтобы увидеть схему и вердикт:

Граница, которую нельзя переступать

Персональные данные владельца не должны попадать в контур Eggent. Агент Eggent имеет bash и полный доступ к файлам без аудита и подтверждений — размещение там контактов, финансов и переписки ломает всю модель приватности, ради которой строится personal-assistant. Обмен только обезличенными задачами и артефактами, направление PA → Eggent, результаты возвращаются как файлы через типизированный intake.

Что полезного взять из Eggent

12 идей. Рантаймы несовместимы (pi-coding-agent ↔ Mastra), поэтому почти всё переносится как паттерн, а не копипаст — кроме транскрайбера, он практически автономен. Лицензия MIT позволяет заимствовать код с указанием авторства.

Важная дополнительная информация

Состояние проекта Eggent

  • Активен: релиз 0.2.0 — 22 июля 2026 (вчера), свежие коммиты, публичный репозиторий eggent-ai/eggent, лицензия MIT.
  • Несостыковка версий: README заявляет «Current version 2.0», а package.json и CHANGELOG — 0.2.0. Маркетинговое округление; ориентироваться на 0.2.0.
  • Двойной рантайм: живой чат идёт через pi SDK, но в коде остался большой legacy-слой собственного агентского цикла (src/lib/agent/agent.ts ~42 КБ, src/lib/tools/tool.ts ~61 КБ) — при чтении кода легко изучать «мёртвый» путь.

Риски Eggent как продукта (если бы мы на него опирались)

  • критично Агент с bash/файлами/кодом без аудита и подтверждений — несовместимо с нашей моделью персональных данных.
  • важно Планировщик живёт в памяти процесса: после рестарта задания не восстанавливаются (признано в README). Наш D.0 должен строиться на персистентном сторе — этот анти-паттерн повторять нельзя.
  • важно Файловые JSON-сторы без транзакций и конкурентного доступа — единственный инстанс, риск гонок.
  • важно Пароль по умолчанию admin/admin (принудительная смена при онбординге есть, но дефолт слабый); данные в data/ не шифруются.

Что Eggent делает хорошо (и это подтверждает наши решения)

  • Локальный best-effort STT без внешних API — приватность как фича.
  • Таймауты, timingSafeEqual, маскирование токенов, дедупликация Telegram-обновлений, docker-hardening (multi-stage, non-root, проверка утечки src/ и .git в образ).
  • Простая файловая память memory.md вместо преждевременного RAG — подтверждает наш выбор отложить vector search.
  • «Тонкий мост» над готовым агентским рантаймом вместо своего цикла — та же ставка, что у нас на Mastra.
