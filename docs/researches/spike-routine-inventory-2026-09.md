## Спайк 1. Извлечение `routineLabel` и `recurrence`

### Метод

Для 54 сообщений взят сохранённый bounded context контура `activity_transaction`; для остальных доступных source messages prompt восстановлен тем же production builder-ом. Скрипт читал только экспорт и ничего не писал в PostgreSQL/MinIO.

В activities встречается 151 distinct `sourceMessageId`: payload доступен для 149 сообщений, а 7 из 386 activities ссылаются на два отсутствующих в экспорте сообщения. Успешно обработаны все 149 доступных сообщений. Извлечённые элементы сопоставлены с сохранёнными activities по source message и уже сохранённым closed facets; поэтому метрики ниже считаются по всем 386 activities, а недоступные или несопоставленные элементы учитываются как omit, то есть оценка coverage консервативна.

Проверку PII по полному набору извлечённых labels выполнил worker-агент спайка (файл ручной разметки методолога остался пустым); при сведении (`mnt-6fba.5`) она подтверждена regex-lint по правилам §2.8 RFC — 0 срабатываний на 223 различных labels. Это не falsifier самого правила §2.3 — правило корректно требует omit, — но подтверждает необходимость фразы приглашения §2.10 про длительность и частоту. ## Спайк 2. Склейка синонимов

### Метод

На 288 labeled activities спайка 1 сравнены три точки применения LLM при неизменном детерминированном пути отчёта:

1. вариант A применяет только формулу `routineKey` из §2.4 RFC: lowercase, trim, collapse whitespace и удаление пунктуации;
2. вариант B дважды независимо запускает прототип `routine-aliases suggest` на одном списке из 223 distinct `routineKey`; модель получает только ключи и число наблюдений, возвращает alias-файл, а методолог построчно принимает, удаляет или перенаправляет каждую предложенную строку;
3. вариант C повторяет extractor-прогон спайка 1, но добавляет существующие labels того же участника как необязательные кандидаты для reuse. Это безопасная нижняя оценка идеи §7: labels других сотрудников не показывались агенту участника, чтобы не переносить их слова через owner boundary. Результат снова нормализуется детерминированно.

Для вариантов B и C использована production-модель из исходных traces (`openai/nath/gpt-5.6-terra`). Первый вызов с текущим локальным `LLM_MODEL=openai/gpt-5.5` вернул `usage_limit_reached`, поэтому модель была явно зафиксирована на trace-version спайка 1. Все входы, prompts, alias-файлы и ручная разметка остались вне репозитория; в PostgreSQL/MinIO спайк не обращался.

В метриках варианта B alias-файл применяется транзитивно; canonical name может быть новым безопасным noun phrase, а не только одним из входных ключей. Вариант C получает только labels, которые уже были извлечены у того же участника за весь цикл: это намеренно измеряет максимальную сходимость при reuse и не моделирует хронологический cold start.

| --- | ---: | ---: | ---: | ---: | ---: |

| B — проверенный alias-файл | 288 | 202 | 70,1 | 70 | 24,3 % |

Вариант B предложил 21 alias-строку; методолог принял все 21 без правки, то есть доля исправленных строк — 0 %. После aliases число рутин уменьшилось на 9,4 %, а покрытие топ-10 выросло на 5,9 процентного пункта. При повторном запуске модель предложила 24 строки: полностью совпали 17 строк из объединения 27 предложений (63,0 %), итоговый canonical key совпал для 95,5 % исходных ключей, а Jaccard по фактически склеенным парам составил 80,6 %. Это подтверждает, что LLM-вывод нельзя применять непосредственно в recompute; проверенный файл нужен как версионируемый детерминированный вход.

Вариант C извлёк label ещё для 39 activities и не потерял labels варианта A. Среди activities, labeled в обоих прогонах, тот же normalized key сохранился у 220 из 288 (76,4 %); 297 из 327 результатов (90,8 %) совпали с одним из ранее существовавших labels этого участника. Однако общегрупповая фрагментация почти не уменьшилась: покрытие топ-10 осталось 18,7 %, рядом с вариантом A. Рост coverage extractor-а нельзя смешивать с качеством межличностной склейки; в текущей безопасной owner-scoped форме reuse не заменяет alias-файл.

### Вывод и falsifier

Первый falsifier сработал: без aliases топ-10 покрывает только 18,4 % labeled activities, существенно меньше половины. Ответ на открытый вопрос §8.1: **alias-файл нужен уже в первом цикле**; одних `variants` в internal DTO недостаточно.

Второй falsifier не сработал: методолог исправил 0 % предложенных строк, ниже порога ~30 %. Misfit §2.4 для проверяемого alias-файла не обнаружен, поэтому вариант C не поднимается из «пересмотреть». Reuse может повышать долю labeled activities и сходимость терминов одного участника, но для межличностных синонимов остаётся post-pilot гипотезой; перед передачей labels между участниками потребуется отдельное решение owner/company/group boundary.

Рекомендация для первого цикла остаётся как в §2.4 RFC: модель предлагает alias-файл, методолог проверяет его, а команда отчёта применяет проверенный артефакт без сети. Неполная воспроизводимость двух suggestion-запусков дополнительно запрещает LLM-склейку внутри пути отчёта.

### Ответы по четырём вопросам §2.1

1. **Куда уходит время — да, с ограничением.** Категории и routines ранжируются по ≈часам, показана доля известных часов и `unsizedObservations`; из-за 40,7 % unsized вывод остаётся порядком величины.
2. **Что повторяется — да.** Отчёт называет routines, observations и contributors. Alias-файл улучшает читаемость отдельных строк, но не устраняет общую фрагментацию: 202 routines на 288 labeled activities. `statedRecurrence` пуст, потому что сотрудники ни разу явно не назвали частоту.
3. **Что нудно или мешает — да.** Раздел по трению формируется из сохранённых `routinePattern` и двух energy markers; пять верхних строк получают видимый сигнал. Energy evidence почти отсутствует (2 из 386), поэтому ответ опирается главным образом на friction patterns.
4. **Что быстро упростить — нет, как надёжный ответ.** Документ формально показывает quick wins, но пустой `automationCandidate` отключает четыре из девяти catalog rows, а matching только по широкому `routinePattern` даёт заметно неточные рекомендации. Методолог не может передать этот раздел как обоснованный без построчной редакторской правки.

### Граница §3.1 и preflight

Client DTO прошёл структурную границу шаблона: нет subject/employee/user/participant IDs, списков contributors, raw messages/цитат, source message IDs, trace payload/IDs, evidence refs, research notes, human-label notes, `variants` или `routineKey`. Редкие routines одного contributor остаются агрегированными `hypothesis` без роли и персональной оценки. Markdown не обещает prerequisites, ROI, экономию или 30/60/90 и явно выносит неизвестное в deep-dive.

Regex-прототип дал 0 findings, в том числе 0 `severity = high`; после ручного review labels ложных пропусков PII не найдено. На этом корпусе high не является рабочим стоп-сигналом: данных о качестве такого отказа нет, а автоматически блокировать client DTO из-за непросмотренного high означало бы дублировать ручной publish gate. Ответ на §8.2: **findings только информируют и требуют решения методолога; команда отчёта не отказывает в формировании client DTO.** Scope mismatch и structurally forbidden fields по-прежнему прекращают подготовку целиком.

### Вывод и falsifier

Falsifier спайка сработал по первому условию: четвёртый вопрос §2.1 не получает достаточно надёжного ответа. Второе условие формально не сработало — две catalog rows совпали с тремя routines топ-5, — но это не подтверждает assumption каталога: один из ключевых facets отсутствует во всём живом корпусе, четыре строки недостижимы, а несколько совпадений по широкому `routinePattern` ложноположительны.

Зафиксирован misfit §2.7/§2.8: стартовый каталог нельзя принимать в реализацию в текущем виде. Предлагаемая правка RFC — каждый quick win должен требовать подтверждения не только facet-триггером, но и проверяемым routine-label/routine-key matcher либо явным `automationCandidate`; extractor или canonical export должен заполнять и сохранять `automationCandidate`, а при отсутствии подтверждения routine уходит в `deepDive`, а не получает рекомендацию. После этой правки структура DTO и семь разделов §2.8 остаются пригодными; пересмотр нужен matching-правилу, а не отчётной границе.

### Оговорки о методе

- Роль «методолога» во всех трёх спайках исполнял worker-агент: review labels, приёмка alias-строк и чтение клиентского Markdown. Человеческая проверка не проводилась и остаётся частью первого живого цикла.
- Повторный прогон extractor совпал с сохранёнными facets в 42,6 % сравнений; спайковые labels — не реконструкция production-транзакций, а новая разметка тем же prompt.
- `automationCandidate` в экспорте выводится, когда заполнен в БД (`postgres-research-corpus-source.ts`). У Green-line он пуст и у 158 activities из 77 транзакций текущего контура `activity_transaction`: prompt требует явной automation opportunity, а не повторяемости, и модель ни разу её не увидела; там же `routinePattern` и `energyStressMarker` заполнены по 2 раза. Пустой facet — свойство живого самоотчёта, а не версии taxonomy.
- Семейная склейка при сведении — ручная regex-эвристика по объектам работы, не результат `routine-aliases suggest`; она задаёт целевой уровень для prompt alias-шага, а не заменяет его.
