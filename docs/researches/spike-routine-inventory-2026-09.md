## Спайк 2. Склейка синонимов

### Метод

На 288 labeled activities спайка 1 сравнены три точки применения LLM при неизменном детерминированном пути отчёта:

1. вариант A применяет только формулу `routineKey` из §2.4 RFC: lowercase, trim, collapse whitespace и удаление пунктуации;
2. вариант B дважды независимо запускает прототип `routine-aliases suggest` на одном списке из 223 distinct `routineKey`; модель получает только ключи и число наблюдений, возвращает alias-файл, а worker-агент в роли методолога построчно принимает, удаляет или перенаправляет каждую предложенную строку;
3. вариант C повторяет extractor-прогон спайка 1, но добавляет существующие labels того же участника как необязательные кандидаты для reuse. Это безопасная нижняя оценка идеи §7: labels других сотрудников не показывались агенту участника, чтобы не переносить их слова через owner boundary. Результат снова нормализуется детерминированно.

Для вариантов B и C использована production-модель из исходных traces (`openai/nath/gpt-5.6-terra`). Первый вызов с текущим локальным `LLM_MODEL=openai/gpt-5.5` вернул `usage_limit_reached`, поэтому модель была явно зафиксирована на trace-version спайка 1. Все входы, prompts, alias-файлы и ручная разметка остались вне репозитория; в PostgreSQL/MinIO спайк не обращался.

В метриках варианта B alias-файл применяется транзитивно; canonical name может быть новым безопасным noun phrase, а не только одним из входных ключей. Вариант C получает только labels, которые уже были извлечены у того же участника за весь цикл: это намеренно измеряет максимальную сходимость при reuse и не моделирует хронологический cold start.

| A — только нормализация | 288 | 223 | 77,4 | 53 | 18,4 % |

Вариант B предложил 21 alias-строку; worker-агент в роли методолога принял все 21 без правки (0 % исправленных строк; человеческая приёмка не проводилась). После aliases число рутин уменьшилось на 9,4 %, а покрытие топ-10 выросло на 5,9 процентного пункта. При повторном запуске модель предложила 24 строки: полностью совпали 17 строк из объединения 27 предложений (63,0 %), итоговый canonical key совпал для 95,5 % исходных ключей, а Jaccard по фактически склеенным парам составил 80,6 %. Это подтверждает, что LLM-вывод нельзя применять непосредственно в recompute; проверенный файл нужен как версионируемый детерминированный вход.

Среди activities, labeled в обоих прогонах, тот же normalized key сохранился у 220 из 288 (76,4 %); 297 из 327 результатов (90,8 %) совпали с одним из ранее существовавших labels этого участника. Однако общегрупповая фрагментация почти не уменьшилась: покрытие топ-10 осталось 18,7 %, рядом с вариантом A. Рост coverage extractor-а нельзя смешивать с качеством межличностной склейки; в текущей безопасной owner-scoped форме reuse не заменяет alias-файл.

### Вывод и falsifier

Первый falsifier сработал: без aliases топ-10 покрывает только 18,4 % labeled activities, существенно меньше половины. Ответ на открытый вопрос §8.1: **alias-файл нужен уже в первом цикле**; одних `variants` в internal DTO недостаточно.

Второй falsifier формально не сработал: агент в роли методолога исправил 0 % предложенных строк при пороге ~30 %. Без человеческой приёмки это не подтверждает assumption §2.4 — она повторяется в спайке 4; вариант C из «пересмотреть» не поднимается. Reuse может повышать долю labeled activities и сходимость терминов одного участника, но для межличностных синонимов остаётся post-pilot гипотезой; перед передачей labels между участниками потребуется отдельное решение owner/company/group boundary.

Рекомендация для первого цикла остаётся как в §2.4 RFC: модель предлагает alias-файл, методолог проверяет его, а команда отчёта применяет проверенный артефакт без сети. Неполная воспроизводимость двух suggestion-запусков дополнительно запрещает LLM-склейку внутри пути отчёта.

3. **Что нудно или мешает — да.** Раздел по трению формируется из сохранённых `routinePattern` и двух energy markers; пять верхних строк получают видимый сигнал. Energy evidence почти отсутствует (2 из 386), поэтому ответ опирается главным образом на friction patterns.
4. **Что быстро упростить — нет, как надёжный ответ.** Документ формально показывает quick wins, но пустой `automationCandidate` отключает четыре из девяти catalog rows, а matching только по широкому `routinePattern` даёт заметно неточные рекомендации. Regex-прототип дал 0 findings, в том числе 0 `severity = high`; после review labels агентом ложных пропусков PII не найдено. Ни одного high-случая спайк не наблюдал, поэтому он не различает «отказ» и «информирование» и вопрос §8.2 не закрывает. Предварительно, до синтетического negative case спайка 4, findings информируют, а решение остаётся за ручным publish gate. Scope mismatch и structurally forbidden fields по-прежнему прекращают подготовку целиком.

### Вывод и falsifier

Falsifier спайка сработал по первому условию: четвёртый вопрос §2.1 не получает достаточно надёжного ответа. Предлагаемая правка RFC — каждый quick win должен требовать подтверждения не только facet-триггером, но и проверяемым routine-label/routine-key matcher либо явным `automationCandidate`; extractor или canonical export должен заполнять и сохранять `automationCandidate`, а при отсутствии подтверждения routine уходит в `deepDive`, а не получает рекомендацию. После этой правки структура DTO и семь разделов §2.8 остаются пригодными; пересмотр нужен matching-правилу, а не отчётной границе.

## Спайк 4. Финальный alias-шаг и negative case preflight

### Метод

Финальный prompt `routine-aliases suggest` собран по §2.4 и §2.7 RFC и дважды независимо прогнан production-моделью исходных traces (`openai/nath/gpt-5.6-terra`) на одном наборе из 223 distinct `routineKey` / 288 labeled activities. Модель видела для каждого ключа только число observations, распределения `taskCategory` и `system`; `subjectKey` ей не передавался. Prompt требовал ровно одну alias-строку для каждого ключа, включая одиночные, склейку до уровня «объект работы + класс действия» и ровно одно назначение закрытого каталога либо `deep_dive` для каждого канонического имени. Скрипт детерминированно добавил `scope`, `basedOn`, `suggestedBy` и `provenance` по исходным ключам.

Первый прогон выбран как кандидат для человеческой проверки в `mnt-6fba.7`; это ещё **не проверенный alias-файл**. Во внешнем операторском контуре подготовлен review-pack: все 288 labels с полями PII/уровня рутины, 75 канонических alias-групп с решением «принять / удалить / перенаправить» и 75 назначений quick win с решением «принять / заменить / deep_dive». Payload, labels и subject keys в репозиторий не копировались.

Для §8.2 отдельно собран синтетический client draft с идентифицирующим `routine.name` и рутиной из топа без строки alias-файла. Prototype flow выполнил lint, сформировал unreviewed high findings, показал их в представлении методолога, попытался пройти publish gate и записал решение в audit. Это проверка поведения прототипа, а не изменение runtime-кода.

Negative case не сработал как falsifier: high доходит до методолога, явно не является проверенным и решение фиксируется. Прототип поддерживает вариант **блокировать publish при unresolved high**, а не только информировать; окончательное решение §8.2 остаётся за оператором в `mnt-6fba.7`.

### Вывод и falsifier

Falsifier воспроизводимости **сработал**: canonical key agreement 40,8 % существенно ниже 90 %. Один из двух запусков также дал покрытие топ-10 49,0 %, ниже порога 50 %; кандидат review (первый запуск) даёт 60,8 %, но до человеческой проверки это не «покрытие по проверенному файлу». Следовательно, предложенный prompt уровня рутины не подтверждает assumption §2.4 в текущей формулировке: модель нестабильно выбирает канонические имена и границы групп, хотя полный alias-файл и provenance технически формируются корректно.

Зафиксирован misfit §2.4/§2.7: перед реализацией нужен либо более жёсткий двухфазный контракт (сначала стабильные group IDs/членство, затем отдельное именование и назначение quick win), либо возврат к лексическим alias-ам; quick win нельзя считать подтверждённым, пока методолог не проверит 75 назначений первого прогона. Доли PII, ложных склеек и человеческих правок заполняются только в `mnt-6fba.7`; агентская проверка их не заменяет.

## Спайк 5. Справочник рутин и extractor с `routineId`

### Метод

Как и в спайках 1–4, runtime-код, PostgreSQL и MinIO не изменялись: экспериментальные скрипты и все входы/выходы остались во внешнем операторском контуре.

Во внешнем операторском контуре из всех проверенных файлов спайка 4 собран `routine-directory.company_green_line.json` v1. Две ложные крупные склейки методолога разделены по классу действия: оформление договоров отделено от отправки документов, подготовка КП — от отправки КП; 19 перенаправленных мелких групп включены в указанные методологом рутины. Затем записи разделены по `roleId` из corpus, поэтому одна каноническая работа в разных ролях имеет разные `routineId`. Получилось 81 role-scoped запись в пяти ролях; это выше предварительной оценки ≈58, потому что разделение по ролям размножает общие названия и v1 сохраняет также однократные проверенные работы. Запись содержит безопасные `name`, `description`, до восьми `examples`, проверенное назначение `quickWin`/`deep_dive`, заметку методолога и `provenance`; сам файл, labels и subject keys остаются вне репозитория.

Extractor дважды независимо прогнан production-моделью исходных traces (`openai/nath/gpt-5.6-terra`) по всем 149 доступным source messages. К production prompt добавлялась только секция справочника роли (id, имя, описание, примеры) и контракт: при ясном соответствии вернуть `routineId`, иначе свободный `routineLabel`; роль как отдельное поле и raw labels других сотрудников модели не показывались. Как в спайке 1, результаты сопоставлялись с 386 сохранёнными activities по source message и закрытым facets, а два отсутствующих сообщения учитывались как omit.

После каждого extractor-прогона отдельно запускался прототип `routine-directory suggest` по distinct свободным `(roleId, routineKey)`. Он предлагал существующую запись, новую запись или `leave_free`; размером остатка для методолога считается только действие над справочником (`existing` или `new`), а не строки `leave_free`, которые по контракту остаются свободными.

### Метрики

| Метрика | Прогон 1 | Прогон 2 |
| --- | ---: | ---: |
| Activities с `routineId` | 295 / 386 (76,4 %) | 292 / 386 (75,6 %) |
| Activities со свободным label | 28 | 31 |
| Omit обоих полей | 63 | 63 |
| Distinct свободных `(roleId, routineKey)` | 27 | 30 |
| Activities топ-10 среди назначенных `routineId` | 162 / 295 (54,9 %) | 160 / 292 (54,8 %) |
| Suggest: существующая / новая / оставить свободной | 10 / 0 / 17 | 13 / 1 / 16 |
| Остаток действий для методолога | 10 | 14 |

Оба прогона назначили `routineId` одним и тем же 284 activities; у 266 из них id совпал, то есть agreement — **93,7 %**. Ещё 19 activities получили id только в одном прогоне; если считать совпадение `routineId` вместе с одинаковыми omit/free исходами по всем 386 activities, полное agreement — 90,4 %. Это существенно выше 40,8 % совпадения canonical key в свободной склейке спайка 4 и проходит порог 90 % по основной метрике назначенных id.

Suggest-шаг увидел 17 одинаковых свободных ключей в обоих прогонах; решение и целевая запись совпали для 12 (70,6 %). Это ниже стабильности extractor-а, но его результат не идёт в отчёт без проверки: важная для §2.4 нагрузка составила 10 и 14 действий, а не 75 групп спайка 4. Расхождение числа входных строк (27/30) происходит раньше suggest — из-за односторонних назначений extractor-а — и не создаёт скрытой недетерминированности report path.

### Вывод и falsifier

Все три falsifier-а спайка **не сработали**: agreement `routineId` 93,7 % ≥ 90 %; coverage 75,6–76,4 % ≥ 60 %; остаток 10–14 строк ≤ 20. Assumption §2.4 подтверждён на Green-line: фиксированные role-scoped границы и имена справочника делают основной extractor-выход воспроизводимым, а человеку оставляют малый review-pack вместо повторной сплошной группировки.

Оговорка для реализации: предварительная оценка справочника «40–60 на группу» оказалась занижена при однократных записях и строгом role scope — v1 содержит 81 запись. Это не falsifier качества, но эпик реализации должен считать prompt budget на наблюдаемом размере и не предполагать 10–20 записей в каждой роли. Suggest остаётся только генератором предложений: его agreement 70,6 % подтверждает необходимость проверки методологом, уже записанную в §2.4, а не прямого применения.

Сравнение со спайком 4: покрытие топ-10 среди назначенных id около 55 % ниже 60,8 % первого свободного alias-прогона, но теперь оно стабильно между запусками, coverage всех activities выше порога, а review-pack сократился с 75 групп до 10–14 действий. Правка §2.4 не требуется; следующим проверяется каталог quick wins в спайке 6.

## Спайк 6. Расширенный каталог и кандидаты из корпуса

### Метод

Офлайн-прогон использовал тот же production model id исходных traces (`openai/nath/gpt-5.6-terra`). Runtime-код, PostgreSQL и MinIO не менялись. Скрипт и все артефакты эксперимента остались в операторском контуре: baseline-назначения, полный набор кандидатов, review-pack для методолога и агрегированные метрики.

Сначала модель повторно назначила закрытый каталог из 15 строк всем 75 рутинам review-pack спайка 4, видя проверенные имена, варианты и число observations, но не решения методолога. Результат сравнивался с финальными назначениями человека. Шесть пустых `replacement` из review-файла однозначно переведены в новые id §2.7 по комментариям методолога: `document_dispatch`, `api_integration`, `document_base`, `ai_research`, `ai_assistant_calc`, `extraction_sorting`.

Модель читала только имя/описание одной рутины и её сообщения и выбирала: существующий id каталога, кандидат новой строки либо `deep_dive` с вопросом обследования. ### Оговорки о методе

- Роль «методолога» во всех трёх спайках исполнял worker-агент: review labels, приёмка alias-строк и чтение клиентского Markdown. Человеческая проверка не проводилась; по ревью 2026-09-04 она выполняется до принятия RFC (спайк 4, `mnt-6fba.7`), а не в первом живом цикле. Показатели «0 % PII» и «0 % исправленных alias-строк» — результат агента, не человека.
- Повторный прогон extractor совпал с сохранёнными facets в 42,6 % сравнений; спайковые labels — не реконструкция production-транзакций, а новая разметка тем же prompt.
- `automationCandidate` в экспорте выводится, когда заполнен в БД (`postgres-research-corpus-source.ts`). У Green-line он пуст и у 158 activities из 77 транзакций текущего контура `activity_transaction`: prompt требует явной automation opportunity, а не повторяемости, и модель ни разу её не увидела; там же `routinePattern` и `energyStressMarker` заполнены по 2 раза. Пустой facet — свойство живого самоотчёта, а не версии taxonomy.
- Семейная склейка при сведении — ручная regex-эвристика по объектам работы, не результат `routine-aliases suggest`; она задаёт целевой уровень для prompt alias-шага, а не заменяет его.
