# Сбор контента из публичных Telegram-каналов для ИИ-ассистента
### Сводный отчёт по трём независимым ресерчам · июль 2026

---

## TL;DR

Три независимых исследования сошлись в одном выводе: под ваше жёсткое ограничение («не подключать личный TG-аккаунт») и ваш стек (**self-hosted n8n + VPS + Notion + Cloudflare**) оптимальный путь — это **self-hosted RSS-мост (RSSHub или rss-bridge) в HTML-режиме `t.me/s/` на зарубежном VPS → n8n (дедуп + LLM-суммаризация) → доставка в Telegram-бот/Notion**.

Ключевые точки согласия всех трёх ресерчей:

- **Bot API — тупик.** Официальный бот физически не может читать чужие публичные каналы, если владелец не добавил его администратором. Для агрегации чужого списка каналов не подходит в принципе.
- **MTProto (Telethon/GramJS) требует номер телефона** — то есть аккаунт. Даёт максимальную полноту, но нарушает ваше ограничение и несёт риск бана. Годится как **эволюционный fallback** на отдельном техническом аккаунте, не как старт.
- **Безаккаунтный путь реален** через парсинг веб-превью `t.me/s/<channel>` — напрямую или через RSS-мост. Ноль credentials, ноль риска для аккаунта, в рамках публичных данных.
- **VPS держать вне РФ.** Telegram в России фактически заблокирован с середины марта 2026; в Беларуси доступен без VPN. Хостинг — Нидерланды/Финляндия.

**Один нюанс, который поднял только третий ресерч и который важен именно для вас как для продуктовой компании** — см. раздел «⚠️ Юридический риск (ToS + AI)» ниже.

---

## Ключевая архитектурная развилка

Всё решение упирается в один выбор:

**Либо** вы принимаете отдельный сервисный номер (технический аккаунт) → открывается полный доступ через MTProto.
**Либо** вы строите систему поверх web-preview / RSS-мостов → полностью без аккаунта, но с зависимостью от HTML-вёрстки Telegram.

Из официальных API при отказе от аккаунта остаётся только Bot API — а он задачу чтения чужих каналов не решает. Это разворот, определяющий всю дальнейшую архитектуру.

## Анализ по группам

### Группа А. Официальные API Telegram

**Bot API.** Бот получает обновления (`channel_post`, `edited_channel_post`) только для каналов, куда владелец добавил его администратором — у каналов нет открытого вступления для ботов. Метода прочитать историю произвольного `@channel` не существует. Вывод всех трёх ресерчей единодушен: **для сбора из чужих каналов неприменим**. Полезен только на этапе *доставки* готового дайджеста (`sendMessage` вам в личку).

**Client API / MTProto.** Даёт полный доступ как обычному клиенту, читает историю любого публичного канала. Реализации: Telethon, Pyrogram-форки (Hydrogram/Kurigram/Pyrofork), GramJS, TDLib. Общий блокер — **обязателен номер телефона**.

Практика «технических» аккаунтов на виртуальных номерах: Telegram массово банит пулы VOIP-провайдеров, для регистрации нужны физические или не-VOIP SIM. С февраля 2023 коды доставляются преимущественно в активные сессии/на почту/голосовым звонком, что усложняет автоматическую регистрацию. Признаки скорого бана: нарастающие `FloodWaitError` (от минут до суток), автопометка сообщений как спама, невозможность вступать в группы. Для минимизации риска — резидентные прокси, лимитирование запросов, сохранение файлов сессий.

### Группа Б. Безаккаунтные методы

**1. Прямой парсинг `t.me/s/<channel>`.** Страница рендерится на сервере и отдаёт статический HTML с ~15–20 последними постами; для истории — параметр `?before=ID` (на практике до ~1000–2000 старых постов через пагинацию). Даёт: текст, дату, views, автора, media-URL, forward/reply. Ноль авторизации, ноль риска для аккаунта.
*Уязвимость:* агрессивный rate-limit по IP (ошибки `429`, капча) и хрупкость к изменению вёрстки. Стабильность зависит от качества ротации прокси.

**2. RSS-мосты (self-hosted).** Делегируют парсинг вёрстки специализированному ПО, отдают стандартный RSS/Atom/JSON:
- **RSSHub** (~44,5 тыс. звёзд, TypeScript, AGPL-3.0) — маршрут `/telegram/channel/:username`, по умолчанию парсит `t.me/s/`. Богатые фильтры (forward/reply/preview). Опционально переключается на MTProto при заданных `TELEGRAM_SESSION` + `API_ID/HASH`. Есть поддержка MTProto-proxy (`TELEGRAM_PROXY_HOST/PORT/SECRET`) — полезно под вашу географию.
- **rss-bridge** (~8,2 тыс. звёзд, PHP) — `TelegramBridge` для публичных каналов. Легче RSSHub, активно поддерживается (релиз 2025-08-05). Лучший баланс простоты/надёжности как основной или резервный мост.
- **tg.i-c-a.su / TelegramRSS** — мощный (RSS+JSON, медиа без экспирации), но под капотом MadelineProto с **реальным аккаунтом**; публичный инстанс лимитирован (15 req/min, temp-ban на любой ошибке, запрет мультиклиентского доступа). Self-host требует аккаунт.

> ⚠️ **Публичные инстансы RSSHub/rss-bridge использовать нельзя** — быстро ловят IP-баны и FloodWait (задокументированы ожидания `contacts.ResolveUsername` до ~2787 сек). Только self-hosted.

**3. Готовые SaaS / scraper-API.**
- **TG Gateway API** (telegram155 на RapidAPI) — чистый JSON, бесплатный тариф 2500 req/мес (при опросе 10 каналов раз в день расход ~300 req/мес → фактически бесплатно). Минимальное время внедрения.
- **Apify** — готовые акторы «Telegram Channel Scraper». Внимание: часть работает через `t.me/s/` (безаккаунтно), часть — через *чужую MTProto-сессию* провайдера. Проверяйте модель извлечения.
- **RSS.app / FetchRSS** — freemium, Telegram-интеграция часто на платном тарифе. Годятся для «запустить за час».

### Группа В. No-code / low-code коннекторы

Нативные Telegram-ноды в **n8n** и **Make** работают только через Bot API → чужие каналы читать не умеют. Их роль — **оркестрация и доставка**, а не источник. Для источника в n8n используется нода **RSS Read / RSS Trigger** поверх self-hosted RSSHub/rss-bridge, либо **HTTP Request** к SaaS-API.

> ⚠️ **Не используйте сервисы с украинскими корнями** (например, Apix-Drive): сервис в одностороннем порядке заблокировал аккаунты пользователей из РФ и РБ без возврата средств. Только self-hosted или нейтральные провайдеры.

## Топ-3 рекомендации

### 🥇 №1 — Self-hosted rss-bridge (или RSSHub) на VPS + n8n
Ложится ровно в ваш стек, без TG-аккаунта (HTML-режим `t.me/s/`), ноль риска бана, в рамках ToS, RSS — идеальный вход для n8n. **rss-bridge** проще; **RSSHub** берите, если нужны богатые фильтры и upgrade-path на MTProto без переписывания пайплайна. Оптимальный старт.

### 🥈 №2 — Прямой `t.me/s/`-парсер на Cloudflare Workers / VPS
Максимальный контроль, минимум зависимостей. У вас уже есть Cloudflare Workers — лёгкий воркер забирает и парсит HTML, отдаёт JSON в n8n. Минус: сами поддерживаете селекторы при смене вёрстки. Важно: MTProto в Workers **не запустится** — только HTML-парсинг.

### 🥉 №3 — SaaS как быстрый старт / бэкап
**TG Gateway API** (бесплатно под ваши объёмы) или **Apify** — «завести за час» без своей инфраструктуры. Хорош как временное решение или горячий бэкап к self-hosted источнику.

> **Эволюционный слой (не старт):** MTProto через отдельный технический аккаунт (TDLib/GramJS) — включать точечно только для каналов, которые не отдаются через web-preview.

## Целевая архитектура (Вариант №1)

**1. Источник.** Список каналов (`username`, вкл/выкл, приоритет, последний собранный `message_id`, режим `preview`/`api-fallback`) — в Notion-базе или n8n static data. Редактируется без деплоя.

**2. Сбор.** Docker-контейнер rss-bridge/RSSHub на VPS вне РФ. В `.env` — кэширование (минимизация запросов к Telegram) и пул ротируемых SOCKS5/HTTP-прокси. Schedule Trigger в n8n на 07:00 → по каждому каналу нода **RSS Read** / **HTTP Request**.

**3. Дедупликация.** n8n сверяет `message_id`/ссылку с уже виденными (Notion / Postgres / n8n static data), пропускает только свежее за сутки.

**4. Хранение.** Таблица `tg_posts_raw`: `channel`, `message_id`, `url`, `published_at`, `edited_at`, `text_plain`, `views`, `media_links`, `source_type`, `fetched_at`, `hash`. Отдельно `channel_state` с watermark по каждому каналу — переживает повторные запуски и edited-посты.

**5. Суммаризация.** Отдельный stage, читающий только нормализованные записи из БД (не ходит в Telegram напрямую). n8n → LLM (Claude / OpenAI / локальный Ollama) с промптом «утренний дайджест за сутки, сгруппировать по темам, дать ссылки». Развязка сбора и суммаризации упрощает дедуп и фильтрацию.

**6. Доставка.** Готовый дайджест → ваш Telegram-бот (`sendMessage` в личку — тут Bot API к месту) и/или Notion / email.

## Инфраструктурные риски для Беларуси

**Локация VPS.** Telegram в РФ фактически заблокирован с середины марта 2026 (замедление подтверждено РКН 10.02.2026, блокировка 14–15 марта). В РБ `t.me` и MTProto доступны без VPN, но фиксировались перебои в периоды «учений». **Вывод: коллектор — только на VPS в ЕС (Нидерланды/Финляндия), не в РФ.**

**Домены Cloudflare Workers.** `workers.dev` и `pages.dev` массово блокируются ТСПУ (эксплуатируются фишингом). **Обход:** не обращаться к `*.workers.dev`, а привязать в панели CF собственный домен (Custom Domain) к воркеру — запросы к своим доменам проходят штатно.

**Прокси.** Для скриптов сбора — ротируемый пул резидентных SOCKS5/HTTP-прокси, чтобы не локализовать парсинг на одном статическом IP хостинга.

**Хрупкость HTML.** Любое изменение вёрстки `t.me` ломает все HTML-парсеры одновременно (RSSHub, rss-bridge, свой воркер). Держите бэкап-источник и мониторинг: нода **Error Trigger** в n8n → уведомление при пустом фиде. RSSHub-сообщество чинит селекторы за часы — нужен лишь перезапуск контейнера.

**Полнота web-preview.** Часть каналов (порнография/копирайт/политика по классификации Telegram) не отдаётся через превью. Если >20–30% нужных каналов недоступны в HTML-режиме — только тогда рассматривайте MTProto-fallback.

## ⚠️ Юридический риск (ToS + AI) — важно для вас как для продуктовой компании

Этот пункт поднял только один из трёх ресерчей, но для вас он критичен: вы строите продукты для клиентов, а не только личный дайджест.

Telegram в Terms **отдельно запрещает data scraping**, а в API Terms — использование данных Telegram для **training / fine-tuning / development / enhancement / deployment** AI/ML-систем. То есть напряжение возникает не только на этапе сбора, но и на всей цепочке, если TG-данные становятся входом для AI-функционала.

Градация риска:
- **Личный утренний дайджест для себя** — риск минимальный.
- **Внутренний инструмент Института «Алгоритм»** — риск умеренный, стоит держать в голове.
- **Коммерческий SaaS-продукт на этой схеме для клиентов** — риск существенный, требует отдельной оценки.

Инженерно систему построить можно. Но при упаковке этого в клиентский продукт стоит развязать «сбор публичных постов» и «AI-обработку» и оценить policy-риск осознанно.

## Итоговый план действий (по шагам)

1. **День 1.** Поднять **rss-bridge в Docker на VPS вне РФ**. Проверить 3–5 ваших каналов: `?action=display&bridge=Telegram&username=@channel&format=Atom`. Отдаются — это ваш прод-источник.
2. **Параллельно.** Собрать пайплайн в n8n (RSS → дедуп → LLM → бот), обкатать на одном тестовом канале.
3. **Бэкап.** Держать наготове TG Gateway API (RapidAPI) или Apify-актор — переключить источник за минуты при поломке парсера.
4. **Мониторинг.** Error Trigger в n8n → уведомление в Telegram при пустом фиде.
5. **Порог апгрейда.** Если часть каналов не читается через web-preview — добавить **отдельный технический аккаунт** (не личный!) и перевести только проблемные каналы на MTProto (TDLib/GramJS). Принять риск бана и заложить ротацию IP.

**Одной фразой:** лучший старт — RSS-first архитектура (self-hosted rss-bridge/RSSHub + n8n) без всякого аккаунта; лучший апгрейд — selective MTProto-fallback на отдельном тех-аккаунте только там, где превью не справляется.
