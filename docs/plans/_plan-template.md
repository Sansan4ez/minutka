## 1. Цель фазы

Что пользователь/система получает по итогу, в одном абзаце. Ниже — 2–4 ключевых решения фазы (каждое — прямое следствие RFC, со ссылкой, не изобретение).

## 2. Definition of Done

Чеклист **проверяемых** условий (каждый — команда или spec, не намерение):

- [ ] <доменный тип/порт/адаптер введён>
- [ ] <инвариант> покрыт `SPEC-...`
- [ ] `npm run typecheck`, `npm run specs`, `npm run verify` проходят
- [ ] <ручной smoke, если нужен>
- [ ] Коммиты по шагам (см. §6)

## 4. Архитектурное решение

Подсекции §4.x под задачу. Контракты типов/портов кодом, границы изоляции, где живут мутации. Настоящее время, конкретика. Ссылки на образцы — провенанс; необходимые выдержки, пути, символы и ревизии включаем в дочерние спеки, чтобы агент не искал контекст.

## 5. Error handling & UX

Как путь деградирует при сбое: фолбэк/backstop, что видит пользователь, какой инвариант сохраняется даже при ошибке (например, «ничего не терять»). Что покрыто spec-ом на error-path.

## 6. Тесты

`SPEC-<AREA>-NNN` через in-memory адаптеры и mock-runner (без LLM/сети): конкретные Given/When/Then с входами, выходами, состоянием и эффектами. NFR — измеримый предел, условия и способ проверки. Persistence/smoke — отдельно, если есть реальное хранилище. Детальные сценарии и необходимые фрагменты test harness включаем в дочерние спеки.

## 7. Порядок работ

Вертикальные срезы; **каждый шаг — отдельный коммит**, заканчивается зелёными typecheck + specs.

1. **<X1> — <что>.** Misfit: ... Проверка: ...
2. **<X2> — <что>.** Misfit: ... Проверка: ...

Перед claim каждый шаг оформляется по [_task-template.md](./_task-template.md): самодостаточная спека, Intent ≤1200, всё описание ≤6000 символов. Если необходимый контекст не помещается — декомпозиция. Контекст зависимых шагов актуализируем после завершения предшественников.

Порядок разблокировки: X1 → X2 → ... (что даёт работающую ценность раньше, что откладываем в конец — durability/провозка).
