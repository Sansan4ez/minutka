# Retention обезличенного среза компании

Обезличенные активности живут только до передачи итогового отчёта компании. Operator-only команда удаляет строки одной компании из `minutka_reporting.anonymized_activities` по `company_id`; личные таблицы сотрудников и срезы других компаний она не затрагивает. Это операционная реализация [RFC §2.5](../architecture/rfc-minutka-tenancy-and-reporting.md#25-retention-данные-живут-до-отчёта) и level-2 transport из [RFC автономности §9](../architecture/rfc-personal-assistant-architecture.md#9-внешние-действия-и-автономность).

Команда не является инструментом агента и не имеет `--yes` или env-bypass. Для непустого среза она работает только в интерактивном TTY.

## Подготовка и preview

Загрузите production-переменные окружения. Команда использует runtime-подключение `DATABASE_URL` и требует обычные обязательные PostgreSQL-переменные (`INVITE_CODE_PEPPER`, `TELEGRAM_IDENTITY_PEPPER`). Перед preview она проверяет отсутствие неприменённых миграций.

Сверьте идентификатор компании контрольным запросом:

```sql
SELECT company_id, count(*)::int AS rows
FROM minutka_reporting.anonymized_activities
WHERE company_id = '<company_id>'
GROUP BY company_id;
```

Запустите команду **не через pipe**, а из интерактивного терминала:

```bash
npm run company:anonymized:purge -- <company_id>
```

Typed use-case сначала читает preview и печатает `companyId` и `expectedRows`. Если `expectedRows = 0`, команда завершает безопасный no-op без challenge и печатает:

```json
{"companyId":"company_acme","expectedRows":0,"deletedRows":0}
```

При непустом срезе команда предупреждает о необратимости и отсутствии backfill, затем требует точную строку:

```text
PURGE <company_id> <expectedRows>
```

Например, для preview `company_acme / 42` нужно ввести `PURGE company_acme 42`. EOF, лишние пробелы, другой `companyId`, другое число строк и запуск без TTY отклоняются; ни одна строка не удаляется.

## Завершение пилота

Порядок действий после завершения взаимодействия с компанией:

1. Выполните и сохраните итоговую выгрузку по процедуре [company-report-export.md](./company-report-export.md).
2. Передайте отчёт компании и зафиксируйте факт передачи вне обезличенной таблицы.
3. Выполните preview/challenge выше и введите точную строку `PURGE <company_id> <expectedRows>`.
4. Сохраните результат:

```json
{"companyId":"company_acme","expectedRows":42,"deletedRows":42}
```

5. Повторите контрольный запрос. Для указанного `company_id` он должен вернуть ноль строк. Повторный запуск является zero-row no-op.

Не удаляйте записи до сохранения и передачи отчёта: по принятому решению backfill из личных данных не строится и не выполняется, поэтому штатная процедура не восстанавливает удалённый обезличенный срез.

## Mismatch между preview и execute

Исполнение принимает `expectedRows` из подтверждённого preview как транзакционный precondition. Если новые строки появились или число строк иначе изменилось до `DELETE`, фактический `deletedRows` не совпадёт с `expectedRows`; PostgreSQL-адаптер делает rollback всей транзакции и команда завершается ошибкой `mismatch` / `run the command again`. Частичного purge нет.

При mismatch:

1. Убедитесь, что источник новых записей для компании остановлен или ожидаемо завершён.
2. Снова запустите `npm run company:anonymized:purge -- <company_id>`.
3. Перечитайте новый preview.
4. Введите новую точную строку `PURGE <company_id> <expectedRows>`.
5. Выполните контрольный SQL-запрос.

Не повторяйте старую строку подтверждения и не удаляйте записи вручную в обход typed-команды.

## Удаление данных сотрудника

Запрос сотрудника на удаление исполняется через отдельный typed use-case и затрагивает только записи с его идентификатором. Обезличенные строки не имеют `employee_id` и при персональном удалении сохраняются. Оператор не сопоставляет их с личными активностями и не удаляет точечно; компенсация этой политики — удаление всего среза компании после отчёта.

## Аварийный сброс

Если в обезличенный след попало запрещённое поле или обнаружена иная ошибка обезличивания, сброс среза компании является штатной аварийной процедурой:

1. Остановите или отключите источник новых записей для затронутой компании.
2. Исправьте причину нарушения и выполните focused verification схемы/typed-действия.
3. Запустите ту же operator-only команду в интерактивном TTY:

```bash
npm run company:anonymized:purge -- <company_id>
```

4. Сверьте preview и введите `PURGE <company_id> <expectedRows>`.
5. При mismatch перечитайте preview и повторите новый запуск; старое подтверждение недействительно.
6. Убедитесь контрольным SQL-запросом, что строк компании не осталось.
7. Возобновите сбор с чистого среза.

Личные данные сотрудников при аварийном сбросе не удаляются. По принятому решению старые обезличенные строки не восстанавливаются: backfill не выполняется, накопление начинается заново.
