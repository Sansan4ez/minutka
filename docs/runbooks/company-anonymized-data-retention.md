# Retention обезличенного среза компании

Обезличенные активности живут только до передачи итогового отчёта компании. Команда ниже удаляет строки одной компании из `minutka_reporting.anonymized_activities` по `company_id`; личные таблицы сотрудников и срезы других компаний она не затрагивает. Это операционная реализация [RFC §2.5](../architecture/rfc-minutka-tenancy-and-reporting.md#25-retention-данные-живут-до-отчёта).

## Подготовка

Загрузите production-переменные окружения. Команда использует runtime-подключение `DATABASE_URL` и требует обычные обязательные PostgreSQL-переменные (`INVITE_CODE_PEPPER`, `TELEGRAM_IDENTITY_PEPPER`). Перед удалением она проверяет отсутствие неприменённых миграций.

Проверьте идентификатор компании и число строк:

```sql
SELECT company_id, count(*) AS rows
FROM minutka_reporting.anonymized_activities
WHERE company_id = '<company_id>'
GROUP BY company_id;
```

## Завершение пилота

Порядок действий после завершения взаимодействия с компанией:

1. Выполните и сохраните итоговую выгрузку по процедуре [company-report-export.md](./company-report-export.md).
2. Передайте отчёт компании и зафиксируйте факт передачи вне обезличенной таблицы.
3. Запустите одну команду удаления:

```bash
npm run company:anonymized:purge -- <company_id>
```

Команда печатает результат вида:

```json
{"companyId":"company_acme","deletedRows":42}
```

4. Повторите контрольный запрос. Для указанного `company_id` он должен вернуть ноль строк. Повторный запуск команды безопасен и возвращает `deletedRows: 0`.

Не удаляйте записи до сохранения и передачи отчёта: по принятому решению backfill из личных данных не строится и не выполняется, поэтому штатная процедура не восстанавливает удалённый обезличенный срез.

## Удаление данных сотрудника

Запрос сотрудника на удаление исполняется через `ProfileStore.deleteEmployeePersonalData(employeeId)` и затрагивает только записи с его идентификатором. Обезличенные строки не имеют `employee_id` и при персональном удалении сохраняются. Оператор не сопоставляет их с личными активностями и не удаляет точечно; компенсация этой политики — удаление всего среза компании после отчёта.

## Аварийный сброс

Если в обезличенный след попало запрещённое поле или обнаружена иная ошибка обезличивания, сброс среза компании является штатной аварийной процедурой:

1. Остановите или отключите источник новых записей для затронутой компании.
2. Исправьте причину нарушения и выполните focused verification схемы/typed-действия.
3. Запустите ту же команду:

```bash
npm run company:anonymized:purge -- <company_id>
```

4. Убедитесь контрольным SQL-запросом, что строк компании не осталось.
5. Возобновите сбор с чистого среза.

Личные данные сотрудников при аварийном сбросе не удаляются. По принятому решению старые обезличенные строки не восстанавливаются: backfill не выполняется, накопление начинается заново.
