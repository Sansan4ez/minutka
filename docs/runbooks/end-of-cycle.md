# Завершение двухнедельного цикла: личный отчёт сотруднику

В конце цикла сотрудник получает свою долю ценности программы — личный итог по собственным данным за период цикла: подтверждённые повторяющиеся рутины, места трения, явно названные сигналы энергии и один вопрос о том, какую рутину он хотел бы упростить. Это отдельный контур: [доказательный отчёт компании](work-retrospective-cycle.md) готовится из разрешённого scoped evidence, не из личного текста отчёта.

Продуктовый источник — [Final_Description §4 «День 14»](../product/Final_Description.md); поведение процесса задано в [`vault/assistant/processes/final_report.md`](../../vault/assistant/processes/final_report.md), окно и подтверждённые паттерны считает `src/application/cycle-activity-summary.ts`, период группы читает `TenantDirectoryStore.getGroupPeriod` из `minutka_reference.training_groups`.

## Что получает сотрудник

Одно сообщение в Telegram по процессу `final_report`:

- повторяющиеся рутины словами сотрудника, места трения и явно названные сигналы энергии за **период учебной группы** (`training_groups.period`, обе даты включительно) — тот же период, по которому отчёт компании отбирает activities; если отчёт запускают до конца периода, окно обрезается сегодняшним локальным днём сотрудника. Участник без записи группы в справочнике получает fallback — последние четырнадцать локальных дней;
- из `routines[]` называются только рутины, которые повторились в цикле **минимум дважды**, с фактической частотой из `count` — отбор делает приложение, а не модель;
- при optional retrospective — личный итог эпизодов за полный период: выбранный шаг, реальные попытки и наблюдения, отдельно от намерений и гипотез. Follow-up добровольный; без retrospective — один вопрос, какую подтверждённую рутину хотелось бы упростить. Ответ — corpus-сигнал для исследовательской команды;
- без часов, каталожных quick wins, выдуманных рекомендаций, обязательных 2–3 шагов, оценок сотрудника и сравнений. Уже выбранный сотрудником шаг не становится требованием; личный итог read-only и не расширяет 72h factual correction window. Historical summary доступна и после конца периода.

Экспорт в файл на пилоте не требуется. Отчёт остаётся в личной истории разговора и живёт по правилам личных данных сотрудника.

## Триггер: ручной запуск оператором на группу

На первом цикле триггер — операторская команда на учебную группу; автоматическое отслеживание `training_groups.period` в пилот не входит.

**Дата запуска не влияет на выборку.** Окно личного отчёта берётся из `training_groups.period`, а не из даты срабатывания, поэтому рассылку можно ставить и через несколько дней после конца цикла: activities после `period.end` в отчёт не попадут, а начало цикла не потеряется. Перед постановкой рассылки проверьте период группы **в production** — в dev-snapshot 2026-09-08 период правился в изолированном клоне, production должен содержать фактические даты прохождения:

```bash
dbq "SELECT id, lower(period) AS period_start, upper(period) - 1 AS period_end FROM minutka_reference.training_groups WHERE id = $1" '["<groupId>"]'
```

Если даты расходятся с реальным прохождением, сначала исправьте справочник тем же операторским путём, которым группа заводилась ([справочники тенантов](tenant-reference-directories.md)), и только затем ставьте рассылку.

```bash
set -a
. ./.env
set +a

npm run cycle:final-reports -- \
  --company company_acme \
  --group group_acme_2026_09 \
  --at 17:00 \
  --preview
```

`--preview` печатает scope, локальное время, число адресатов (`eligible`), число ещё не завершивших онбординг (`notOnboarded`) и строку подтверждения — и выходит, ничего не меняя.

Без `--preview` команда сначала печатает тот же preview, затем требует точное подтверждение:

```text
SEND FINAL REPORT company_acme/group_acme_2026_09
```

Ответ `yes`, флаг `--force` или подтверждение через модель это подтверждение не заменяют. `--at` задаёт **локальное** `HH:MM` каждого сотрудника (по умолчанию `17:00`), поэтому группа в разных часовых поясах получает отчёт в свой рабочий день.

После подтверждения команда печатает исход по каждому `employeeId` — `armed` либо `failed` с безопасным кодом причины без provider payload — и счётчики `armed`/`failed`.

## Что делает подтверждённый запуск

Команда ничего не отправляет сама. Она ставит каждому сотруднику **разовое** расписание `final_report` (`oneShot`, маска дней `127`) через typed use-case `ScheduleManagementService`. Дальше работает обычный контур: планировщик забирает срабатывание, `PersonalAssistantService.runScheduledProcess` выполняет процесс, Telegram-доставка отправляет ответ в личный тред. Идемпотентность даёт существующий ledger `minutka_private.schedule_fires`; после успешного срабатывания разовая строка выключается сама.

Повторный запуск на ту же группу переиспользует ту же строку расписания и переносит время — второго отчёта не появляется.

Расписание `final_report` не входит в личные настройки сотрудника: `listSchedules`, `setDailySchedule` и `disableSchedule` показывают и меняют только утреннее, вечернее и недельное сообщение.

## Если данных мало

Если за цикл записано меньше шести активностей или они попали меньше чем в четыре дня, `readCycleActivities` возвращает `sufficientData: false`. В этом случае ответ прямо говорит, что данных за цикл мало, и ограничивается тем, что есть; паттерн не называется и картина не достраивается.

## Граница личного контура

- **Личный отчёт не входит в артефакт компании.** Компания его не получает; в клиентскую карту не копируются его текст, личные обязательства или эмоциональные оценки. Доверенная исследовательская команда имеет разрешённый tenant-scoped доступ к каноническому разговору, включая личный итог, по consent; нельзя обещать, что исследователь его не видит.
- Процесс `final_report` **read-only**: он не вызывает `collectActivity` и не меняет профиль, поэтому подготовка отчёта не добавляет и не меняет ни одной строки, из которой строится отчёт компании.
- Личный отчёт живёт в личных данных сотрудника, поэтому **удаление обезличенного среза компании его не затрагивает**. Обратное тоже верно: [персональное удаление](employee-personal-data-deletion.md) и [purge по company/group](research-scope-purge.md) удаляют личную историю вместе с остальными личными данными этого сотрудника.

## Порядок операций в конце цикла

1. По private manifest и отдельному разрешению оператора проверить период, выполнить preview, поставить личные final и проверить фактическую доставку. Успешный final заменяет вечернее приглашение того же локального дня; failed/disabled final его не подавляет.
2. Пройти evidence-backed company loop: prepare → operator check → deterministic v3 build → preflight → решения high → operator publish по [`work-retrospective-cycle.md`](work-retrospective-cycle.md). Личный итог не client report; generic quick wins из directory не fallback для текущего пути. Production sends/publish не разрешаются самим runbook.
3. Сохранить private snapshot/feedback и провести полный анализ двух недель. Retention/purge — штатная отдельная процедура: запрос удаления не откладывается ради отчёта; до передачи удаление/исправление evidence требует invalidation/recompute и новой проверки. Уже доставленный client artifact не отзывается автоматически.

## Отказы

Команда завершается ненулевым кодом и печатает явную причину в stderr, если:

- не передан `--company` или `--group`;
- `--at` не является корректным `HH:MM`;
- в группе нет ни одного сотрудника со статусом `profile_completed`;
- подтверждение не совпало (`confirmation did not match; nothing was armed`) — в этом случае не ставится ни одно расписание;
- PostgreSQL недоступен или миграции не применены.

Отдельный сотрудник, для которого расписание поставить не удалось, попадает в исход `failed` и не прерывает остальных.

## Проверка

1. Период группы в production совпадает с фактическими датами прохождения (запрос выше).
2. `--preview` показывает ровно ту группу и то число адресатов, которое ожидает оператор.
3. После подтверждения `armed` равно `eligible`, `failed` равно нулю.
4. `dbq "SELECT process_id, one_shot, time_of_day, timezone, enabled FROM minutka_private.process_schedules WHERE user_id = $1" '["<employeeId>"]'` показывает одну строку `final_report` с `one_shot = true`.
5. После срабатывания есть запись `minutka_private.schedule_fires` с `process_id = final_report` и статусом `succeeded`, а сотрудник получил сообщение в Telegram.
6. Текст личного отчёта репетируется только на изолированном клоне БД (тот же паттерн, что reviewed replay назначений рутин). On-demand запуск `final_report` на production выполняется только для реальной доставки, потому что ход сохраняется в личной истории сотрудника ([runbook](scheduled-process-on-demand.md)).
